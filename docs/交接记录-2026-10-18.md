## 六、环境硬约束（踩过的坑，别再踩）

1. **本机 `github.com:443` 不通**（connection reset），`api.github.com` 通。
   所以 `git push` 永远会失败，必须用 **Git Data API**：`out/push_api2.py` 就是干这个的，
   自动 diff 远端树、建 blob、建树、建提交、推 ref，全部带回读校验。
   （别用 `git push`，别花时间修代理。）
2. **本机没有 node**，`vps-deploy/_gen_installer.mjs` 跑不了。要改 `deploy-astrbot-page.sh`
   只能定向替换对应 heredoc，并且**必须同步改生成器源码**，否则下次谁跑生成器就覆盖回去了。
3. PowerShell 里写 Python 一行流很容易被引号/`%` 咬到 —— 一律**落成 `.py` 文件再跑**。
   （Python 里格式化 shell 的 `%s` / `%n` 要写成 `%%s` / `%%n`。）
4. **PowerShell 的 `>` 重定向会写 UTF-16、并破坏二进制**。抓截图或拉日志一律用
   `cmd /c "... > 文件"`；看含中文的日志也别直接 `Get-Content`（GBK 乱码），
   用 `adb exec-out run-as com.termux cat <文件> > 本机文件` 再读。
5. **GitHub 内容接口会遇到瞬时 `Remote end closed connection`** —— 重试即可，不必怀疑内容。
6. **`git ls-tree` 默认会把中文路径转义**（`core.quotepath=true`），对账时一律加
   `-c core.quotepath=false`，否则会误判「文件一边有一边没有」。
7. **站点对 `Python-urllib` 的默认 UA 返回 403**。用 python 取站点内容要带
   `User-Agent: Mozilla/5.0`（curl 默认 UA 能过）。
8. **下载页出现 +367 B 不是脚本写的**：那是 Cloudflare 注入的
   `static.cloudflareinsights.com` beacon 脚本，磁盘上的文件没变。
9. 设备上的 `grep`/`sed` 在 houdini 转译下**偶发段错误**（Termux aarch64 程序跑在 x86_64 模拟器上），
   看到 `Segmentation fault` 先怀疑它，别急着怀疑 QQ。同理 `sed` 不吃 `\x1b\[...\]` 这种正则。
10. `run-as com.termux /system/bin/sh` 是**非登录 shell**，`$HOME` 是空的 —— 脚本里一律用绝对路径
    `/data/data/com.termux/files/home/.qqbot`。

## 十一、追加记录：v1.1.18（真机 Xvfb 起不来）

**一句话**：真机上 NapCat 启动不起来的根因是 **部署期和运行期用的 proot 参数不一致** ——
运行期把 `--link2symlink` 丢了，而真机 `link(2)` 直接 EPERM。

### 11.1 症状与定位过程

1. 用户报「真机上 napcat 启动不起来，其他都正常，AstrBot 也正常，之前重装过」；
   本机 `adb devices` 里只有 MuMu 两台，**没有真机**，只能靠用户贴的自检输出定位。
2. 真机自检显示：proot / 沙盒目录 / `/tmp` 权限都正常，三档 Xvfb 参数**全部失败**，
   报错是 `Lock file ... failed: Permission denied` + `[Fatal] server error: Failed to establish socket`。
3. `link(2)` 在这台真机上直接返回 EPERM（Redmi / Android 16 一类），
   而 Xvfb 起显示号的第一步就是给 `/tmp/.X<n>-lock` 建硬链接 → 秒退 →
   QQ 等不到 X，20 秒后退出 → supervisor 5 秒后再拉 → 看起来「十分钟都没启动好」。

## 十二、追加记录：v1.1.19（真机 QQ 秒退）

### 12.1 症状：修完 Xvfb，下一层才露出来

1.1.18 补回 `--link2symlink` 之后，真机上 Xvfb 起来了，但 **QQ 紧接着自己秒退**。
用户给的现场是 `<uid>/grep: <pid>/stat: No such file or directory`，shell 里只有
`Trace/breakpoint trap`，NapCat 照样起不来。

从用户上传的错误报告里读到完整因果链（真机 Redmi 24069RA21C / Android 16 / arm64-v8a /
kernel 6.1.138-android14-11）：

```
GLX is not present
Initialization of all EGL display types failed.
FATAL:sandbox/linux/services/proc_util.cc:114
  Check failed: . : Operation not permitted (1)
GPU process isn't usable. Goodbye.
```

两段因果关系：

1. QQ 的 Chromium 会先起一个 GPU 子进程去初始化 EGL。沙盒的虚拟屏幕（Xvfb）没有 GLX，
   这一步必然失败 —— 但这只让它**退到软件渲染**，本身不致命。
2. 致命的是紧接着那一步：它要枚举那个 GPU 子进程的 `/proc/<pid>/fd` 来校验沙箱，
   而 **Android 10 起 `/proc` 对非本进程大幅收紧**，`fstatat()` 直接返回 EPERM。
   连撞三次之后 `GPU process isn't usable. Goodbye.` 把主进程一起带走。

所以病根不是「没有 GPU」，而是「**有 GPU 子进程**」—— 只要让它别去起那个子进程，
`/proc` 那一步根本不会发生。

## 十三、追加记录：v1.1.20（真病因是 Xvfb 色深）

### 13.1 症状与 1.1.19 一模一样

1.1.19 用 `--disable-gpu` 那一档装上真机，结果还是 `Trace/breakpoint trap`，NapCat 起不来。
用户又发了一份错误报告（`out/20261018-203627-13962.txt`，83,435 B），里面的 GL 报错和

```
ANGLE Display::initialize error 12289: GLX is not present.
Initialization of all EGL display types failed.
Exiting GPU process due to errors during initialization
GPU process isn't usable. Goodbye.
```

关键在最后那条日志的顺序：`--disable-gpu` 并没有阻止 GPU 子进程被拉起来，它只是不让
Chromium *使用* 硬件加速。GPU 进程照样初始化 EGL、照样失败、照样把主进程带走 ——
而且因为「没有软件合成可退」，反而死得更干脆。

### 13.2 真病因：屏幕只有 8 位色深

`XVFB_VARIANTS` 的第一档是 `1x1x8 +extension GLX +render`（1 像素 × 8 位色深），
这是照抄参考项目 AstrBot-Bubble-Android-App 的写法。但 **8 位屏没有可用的 GL 配置**，
ANGLE 必然报 `GLX is not present`。

在模拟器上做了决定性实验（`out/gltest2.sh`）：同一份 rootfs、同一个 QQ、只改 Xvfb 的
`-screen` 参数，各跑一次看日志。

| Xvfb 参数 | 结果 | ANGLE/EGL 报错行数 |
| --- | --- | --- |
| `1x1x8 +extension GLX +render` | GPU 进程崩 | 20 |
| `1x1x8` | GPU 进程崩 | 20 |
| `640x480x16` | GPU 进程崩（`No suitable EGL configs found`） | — |
| `640x480x24` | **正常出二维码** | **0** |
| `1280x800x24` | 正常 | 0 |

所以：**只有 24 位色深能让 GPU 进程初始化成功**，8 位没 GL、16 位配不出 EGL config。
之前两版都栽在这个「照抄来的第一档」上。

顺带澄清一个误导性日志：`sandbox/linux/services/proc_util.cc:114 Check failed: . :
Operation not permitted` 是 GPU 进程**退出时**的清理动作（枚举 `/proc/self/fd`），
是症状不是病因 —— 1.1.19 就是被它带偏，去改 QQ 的启动参数了。

### 14.4 本段新踩的坑

1. **`reinstallInfo` 的「当前在干哪一步」写错了**：一开始用「最后一个已出现的阶段」当提示，
   结果阶段 1（清理旧文件）打勾之后，提示还停在「当前：清理旧文件」，而实际上早就在装 NapCat。
   正确做法是取「第一个还没出现的阶段」。
2. **PowerShell 里 `Set-Content -NoNewline -Encoding ascii $path` 会写空文件**：`$path` 会被绑成
   `-Path` 而没有 `-Value`。这类写文件一律用 `[System.IO.File]::WriteAllText`。
3. **heredoc 走 `Out-File -Encoding ascii` 会把中文写成 `?`**：在 Python 脚本里引用中文文件名
   （`使用说明.md`）会直接 `OSError: Invalid argument`。要么把 .py 本身按 UTF-8 落盘，
   要么用 `\uXXXX` 转义写文件名。
4. **`adb shell` 里 `grep` 不可用**（houdini 转译段错误），校验设备上的文件内容要用
   `exec-out run-as com.termux cat > 本机文件`，或改用 `run-as com.termux /data/data/com.termux/files/usr/bin/grep`。
5. **桌面端 QQ 的窗口坐标会漂**：虚拟桌面在 1920 / 3200 / 3840 之间变过（显示器休眠），
   每次点击前都要重新 `EnumWindows` 取 rect，否则会把文件贴到别的会话里。
