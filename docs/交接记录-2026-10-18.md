## 一、一句话现状

**v1.1.26 已经从代码修到线上（详见第十九节）。**

> 现在的状态一句话说完：真机上那个「Worker 退出码 11」**这次是找到真正的根因了** ——
> 不是 NapCat 的进程模型，也不是 QQ 参数，而是 **Termux 的 proot 往每个进程里映射了它自己的
> loader，却只映了文件头 4KB 和代码页，而这个 loader 的节头表在文件偏移 0x45d8（映射之外）**。
> NapCat 注入的 frida-gum 枚举模块时按 `基址 + e_shoff` 去读节头，算出 `0x200000 + 0x45d8 =
> 0x2045d8`（真机 `si_addr` 逐字节对上），那里没有映射 → SEGV_MAPERR。
> 修法是给 loader 打一份「节头清零」的副本挂 `PROOT_LOADER`，不动 Termux、不动 NapCat、不用重装沙盒。

真机这条线的走法：1.1.18 修 `--link2symlink`（Xvfb 能起了）→ 1.1.19 试改 QQ 参数绕 GPU（没成）
→ 1.1.20 找到真病因（Xvfb 色深必须 24 位）→ 1.1.22 加崩溃记录器（能抓了）
→ 1.1.23 修「重装假成功」→ 1.1.24 让记录器接管 `sigaction`（真机终于抓到现场）
→ 1.1.25 按上游 PR #1984 改走 fork（**被真机证明无效**）→ **1.1.26 用崩溃地址反推出 proot loader 越界**。

唯一还没做、也做不了的一步仍然是：**用手机 QQ 扫一次码把 NapCat 登上** —— 必须由人来做。

> **下一步建议（真机）**：装 1.1.26、重启一次服务。要看补丁有没有生效，可以「检查运行环境」，
> 里面有 `loader补丁:` 一行（已启用 / 已生成但没挂上 / 未启用）。若还崩，
> 「上传错误日志」的报告里新增了 `proot loader 补丁` 段，会带上系统 loader 的 `e_shoff`
> 与 `PROOT_LOADER` 的当前值，一眼能看出是不是没挂上。

> **用户约定（2026-10-18 定下）**：**每次更新都要走完整发布链**，不要只给 APK。

## 六、环境硬约束（踩过的坑，别再踩）

1. **本机 `github.com:443` 不通**（connection reset），`api.github.com` 通。
   所以 `git push` 永远会失败，必须用 **Git Data API**：`out/push_api2.py` 就是干这个的，
   自动 diff 远端树、建 blob、建树、建提交、推 ref，全部带回读校验。
   （别用 `git push`，别花时间修代理。）
2. **本机没有 node**，`vps-deploy/_gen_installer.mjs` 跑不了。要改 `deploy-astrbot-page.sh`
   只能定向替换对应 heredoc，并且**必须同步改生成器源码**，否则下次谁跑生成器就覆盖回去了。
3. PowerShell 里写 Python 一行流很容易被引号/`%` 咬到 —— 一律**落成 `.py` 文件再跑**。
   （Python 里格式化 shell 的 `%s` / `%n` 要写成 `%%s` / `%%n`。）
4. **PowerShell 的 `>` 重定向会写 UTF-16、并破坏二进制**。抓截图或拉日志一律用
   `cmd /c "... > 文件"`；看含中文的日志也别直接 `Get-Content`（GBK 乱码），
   用 `adb exec-out run-as com.termux cat <文件> > 本机文件` 再读。
5. **GitHub 内容接口会遇到瞬时 `Remote end closed connection`** —— 重试即可，不必怀疑内容。
6. **`git ls-tree` 默认会把中文路径转义**（`core.quotepath=true`），对账时一律加
   `-c core.quotepath=false`，否则会误判「文件一边有一边没有」。
7. **站点对 `Python-urllib` 的默认 UA 返回 403**。用 python 取站点内容要带
   `User-Agent: Mozilla/5.0`（curl 默认 UA 能过）。
8. **下载页出现 +367 B 不是脚本写的**：那是 Cloudflare 注入的
   `static.cloudflareinsights.com` beacon 脚本，磁盘上的文件没变。
9. 设备上的 `grep`/`sed` 在 houdini 转译下**偶发段错误**（Termux aarch64 程序跑在 x86_64 模拟器上），
   看到 `Segmentation fault` 先怀疑它，别急着怀疑 QQ。同理 `sed` 不吃 `\x1b\[...\]` 这种正则。
10. `run-as com.termux /system/bin/sh` 是**非登录 shell**，`$HOME` 是空的 —— 脚本里一律用绝对路径
    `/data/data/com.termux/files/home/.qqbot`。

## 九、如果还要继续做

**再发下一个版本时，照这个顺序：**

1. 改代码 → `VERSION` 升号 → `.\out\rebuild-all.ps1`；
2. 装机（`adb install -r`）→ 打开启动器 → 确认界面全绿、`scripts.log` 的
   `synced=N failed=0`（每次覆盖安装后这一点最能说明脚本真的下发到设备了）；
3. 更新 `使用说明.md` / `CHANGELOG.md` / `README.md` / `docs/BUILD.md` 里的版本号、大小、校验值；
4. 建 GitHub release + 传 APK 资产（走 API）；
5. 站点：**其实可以什么都不做**，等第二天定时器自己同步；想立刻生效就
   `systemctl start zhuxin-astrbot-dl.service`（比手工传文件靠谱得多）；
6. `vps-deploy/data/astrbot.json` 快照 + 安装脚本内嵌兜底，**顺手跟到新版本**（本次发现它们落后了 11 个版本）；
7. 提交并推送（`out/push_api2.py`）。

> 快照里的 `updated` 字段会随每天同步自然漂移，**不用**天天去追它；只有版本内容明显落后才值得动。

## 十二、追加记录：v1.1.19（真机 QQ 秒退）

### 12.1 症状：修完 Xvfb，下一层才露出来

1.1.18 补回 `--link2symlink` 之后，真机上 Xvfb 起来了，但 **QQ 紧接着自己秒退**。
用户给的现场是 `<uid>/grep: <pid>/stat: No such file or directory`，shell 里只有
`Trace/breakpoint trap`，NapCat 照样起不来。

从用户上传的错误报告里读到完整因果链（真机 Redmi 24069RA21C / Android 16 / arm64-v8a /
kernel 6.1.138-android14-11）：

```
GLX is not present
Initialization of all EGL display types failed.
FATAL:sandbox/linux/services/proc_util.cc:114
  Check failed: . : Operation not permitted (1)
GPU process isn't usable. Goodbye.
```

两段因果关系：

1. QQ 的 Chromium 会先起一个 GPU 子进程去初始化 EGL。沙盒的虚拟屏幕（Xvfb）没有 GLX，
   这一步必然失败 —— 但这只让它**退到软件渲染**，本身不致命。
2. 致命的是紧接着那一步：它要枚举那个 GPU 子进程的 `/proc/<pid>/fd` 来校验沙箱，
   而 **Android 10 起 `/proc` 对非本进程大幅收紧**，`fstatat()` 直接返回 EPERM。
   连撞三次之后 `GPU process isn't usable. Goodbye.` 把主进程一起带走。

所以病根不是「没有 GPU」，而是「**有 GPU 子进程**」—— 只要让它别去起那个子进程，
`/proc` 那一步根本不会发生。

## 十三、追加记录：v1.1.20（真病因是 Xvfb 色深）

### 13.1 症状与 1.1.19 一模一样

1.1.19 用 `--disable-gpu` 那一档装上真机，结果还是 `Trace/breakpoint trap`，NapCat 起不来。


关键在最后那条日志的顺序：`--disable-gpu` 并没有阻止 GPU 子进程被拉起来，它只是不让

而且因为「没有软件合成可退」，反而死得更干脆。

### 13.2 真病因：屏幕只有 8 位色深

`XVFB_VARIANTS` 的第一档是 `1x1x8 +extension GLX +render`（1 像素 × 8 位色深），
这是照抄参考项目 AstrBot-Bubble-Android-App 的写法。但 **8 位屏没有可用的 GL 配置**，
ANGLE 必然报 `GLX is not present`。

在模拟器上做了决定性实验（`out/gltest2.sh`）：同一份 rootfs、同一个 QQ、只改 Xvfb 的
`-screen` 参数，各跑一次看日志。

| Xvfb 参数 | 结果 | ANGLE/EGL 报错行数 |
| --- | --- | --- |
| `1x1x8 +extension GLX +render` | GPU 进程崩 | 20 |
| `1x1x8` | GPU 进程崩 | 20 |
| `640x480x16` | GPU 进程崩（`No suitable EGL configs found`） | — |
| `640x480x24` | **正常出二维码** | **0** |
| `1280x800x24` | 正常 | 0 |

所以：**只有 24 位色深能让 GPU 进程初始化成功**，8 位没 GL、16 位配不出 EGL config。
之前两版都栽在这个「照抄来的第一档」上。

顺带澄清一个误导性日志：`sandbox/linux/services/proc_util.cc:114 Check failed: . :
Operation not permitted` 是 GPU 进程**退出时**的清理动作（枚举 `/proc/self/fd`），
是症状不是病因 —— 1.1.19 就是被它带偏，去改 QQ 的启动参数了。

## 十七、追加记录：v1.1.24（把真机的崩溃现场弄回来）

### 17.1 先确认了一件事：「退出码 11」= SIGSEGV

真机日志里那一行是 `[NapCat] [UtilityProcess] Worker进程退出，退出码: 11`。
它到底是「普通退出码 11」还是「被信号打死」，决定了后面所有排查方向。

做法：在模拟器上找到 NapCat 的 Worker 子进程（`exe --type=utility --utility-sub-type=node.mojom.NodeService`），
`kill -SEGV <pid>`，日志立刻打出：

```
10-19 10:23:57 [error] [NapCat] [UtilityProcess] Worker进程退出，退出码: 11
10-19 10:23:57 [warn]  [NapCat] [UtilityProcess] Worker进程意外退出 (1/3)，正在尝试重新拉起...
```

**一模一样。所以 11 就是 SIGSEGV。**（`Bw = 3`、`O8 = 1e4`：10 秒内崩 3 次，主进程 `process.exit(1)`。）

模拟器崩一次能自己拉起来并正常出二维码；真机是连着崩，所以永远起不来 —— 差别在「崩得多快」，
不在「崩不崩」。

### 17.2 为什么 1.1.22 的崩溃记录器在真机上一份文件都没写

`crashwatch.c` v1 是在 `__attribute__((constructor))` 里装一次 `sigaction`。
但 **Chromium 启动时会自己调 `sigaction()` 把处理器换掉**，等于把我们的顶掉。
于是崩溃全落在 Chromium 的处理器里，我们的代码一次都没被调用 ——
报告里 `crashes/` 一直是空的，不是记录器没编出来（`crashwatch.so` 在、`cw-build.log` 0 字节）。

顺带排除了一个方向：Chromium 自带的 Crashpad 也没用。
`.../qqinst/bot1/.config/QQ/Crashpad/` 里只有一个 `client_id`（36 字节），全盘 `find -name '*.dmp'` 零命中。

### 17.3 改了什么

| 文件 | 改动 |
| --- | --- |
| `build/opt/qqbot/sandbox/crashwatch.c` | **自己导出 `sigaction()`**：应用来装处理器时先记进 `g_app[]`，实际装的是我们的；崩溃时先写现场，再 `chain_to_app()` 把控制权交还给应用原本那个处理器（按 `SA_SIGINFO` 区分 `sa_sigaction` / `sa_handler`），QQ 行为不变。新增 `dump_pc_segment()`：流式解析 `/proc/self/maps`，直接写出「pc 落在哪一段、哪个 .so」。 |

### 17.4 顺手排除的一条路：单进程模式

### 17.6 这轮踩的坑

1. **`ps` 里 QQ 的主进程 cmdline 是 `qq --no-sandbox ...`，不是 `/opt/QQ/qq`** ——
   用 `grep 'opt/QQ/qq'` 会一个都匹配不到，误判成「QQ 没起来」。

### 18.2 根因：Worker 走的是 Electron 的 UtilityProcess

日志顺序是关键证据（真机 `qq-bot1.log`，12:17:36 / :37 / :39 连续三轮）：

- 崩在 WebUI Token 之后：`enableAllBypasses`（`napcat.mjs:83246`）其实**早就跑完了**

### 19.2 崩溃地址把范围缩到一个数

1.1.25 的崩溃记录（`report_1319.txt:594-643`）：

| 字段 | 值 |
| --- | --- |
| signal | `11 (SIGSEGV)`，`si_code=1`（SEGV_MAPERR） |
| **si_addr** | **`0x2045d8`**（5 份记录完全一致） |
| pc | `模块基址 + 0x39EE44`（= `gum_elf_module_load+0x880`，指令 `ldr w1,[x20]`） |
| 模块 | `/opt/QQ/resources/app/app_launcher/napcat/native/napi2native/napi2native.linux.arm64.node` |
| maps 头两行 | `00200000-00201000 r--p …/usr/libexec/proot/loader`，下一段映射在 `0x129e6a4000` |

`si_addr` 在 5 次崩溃里恒定、而模块基址每次都不同（ASLR）→ 说明它不是随机指针，而是
`固定基址 + 固定偏移` 算出来的。`0x2045d8 - 0x200000 = 0x45d8`，正好是
Termux proot loader（`$PREFIX/libexec/proot/loader`，18,136 字节）的 **`e_shoff`**
（`out/check_loader_elf.py` 用 pyelftools 读出：`ET_EXEC`、`entry=0x5400000000`、
`e_shoff=0x45d8`、`e_shnum=4`、`e_shentsize=64`）。

### 19.3 机制：proot 只映 loader 的两段，gum 却按 e_shoff 去读节头

loader 只有两个 PT_LOAD：

- `vaddr=0x00200000 off=0x000000 filesz=0x000120 flags=R` → 运行时只占用 `00200000-00201000` 一页；
- `vaddr=0x5400000000 off=0x004000 filesz=0x000468 flags=RX` → `5400000000-5400001000`。

节头表在文件偏移 0x45d8，**两段都没覆盖**。frida-gum 枚举模块时把 `0x200000` 当模块基址、
按 `e_shoff` 去拷节头，于是读到 `0x2045d8` —— 那里没有任何映射，SEGV_MAPERR。
反汇编（capstone，`vaddr 0x39ED00` 起）还能看到守卫逻辑：`ldrh w1,[x28,#0x92]`（`e_shnum`）
`× ldrh w22,[x28,#0x94]`（`e_shentsize`）与 `e_shoff` 相加后 `cmp x20,x1; b.eq` ——
**`e_shnum=0` 时整段拷贝循环直接跳过**，这正是补丁下手的点。拷贝步长 `lsl x3,x2,#6` = 64 字节，
也正好是 `Elf64_Shdr` 的大小。

### 19.4 修法：给 loader 一份「节头清零」的副本

`build/opt/qqbot/common.sh` 在 `export PROOT_TMP_DIR` 之后新增：

- `qq_loader_patched()`：用 `dd … | tr -d '\000'` 判断偏移 0x28 的 8 字节与 0x3C 的 4 字节是否全 NUL；
- `qq_make_loader_fix()`：`cp` 到 `$QQBOT_HOME/proot-loader`、`chmod 755`，再两条
  `dd if=/dev/zero of=… bs=1 seek=40/60 count=8/4 conv=notrunc` 清零 `e_shoff` 与 `e_shnum`+`e_shstrndx`；
- `qq_proot_fix_loader()`：只在用的是 Termux 那份 proot（`$PREFIX/bin/proot`）时生效，
  源文件更新或补丁丢失就重做，然后 `export PROOT_LOADER=…`（顺带 `PROOT_LOADER_32`）；
- `qq_proot_selftest()` 加了自动回退：带补丁自检失败时 `unset PROOT_LOADER` 再试一次，
  成功就删掉补丁文件并提示「loader 补丁与当前 proot 不兼容，已回退」。

为什么清零是安全的：内核执行程序只读 program header，节头表只服务于工具；loader 本身是
`ET_EXEC` 的两段小桩，运行期不会回头读自己的节头。删掉 `PROOT_LOADER` 即可完全回退。

### 19.7 这一节的踩坑

1. **静态可达性分析是死路**：`gum_elf_module_load` 的调用方全走 GObject 虚表，静态调用图看不进去；
   真正有用的是**拿崩溃地址做算术**（`si_addr - 映射基址 = e_shoff`）。
2. **VPS 上没有 `unzip`**：校验 NapCat 发行包要用 `python3 -c "import zipfile …"`。
3. **两个 curl 抢同一个输出文件**：本地那次超时留下的远程 curl 还在写，新任务又开了一个，
   文件大小会莫名变大 —— 起任务前先 `pgrep -af curl` 看一眼。
4. **PowerShell 会把 `python -c "…"` 与管道里的 `tail` 吃掉**：一律写成 `.py` / `.sh` 文件再跑。
5. **`run-as com.termux bash …` 会 Permission denied**：要写全路径
   `/data/data/com.termux/files/usr/bin/bash`。
