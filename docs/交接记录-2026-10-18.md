## 六、环境硬约束（踩过的坑，别再踩）

1. **本机 `github.com:443` 不通**（connection reset），`api.github.com` 通。
   所以 `git push` 永远会失败，必须用 **Git Data API**：`out/push_api2.py` 就是干这个的，
   自动 diff 远端树、建 blob、建树、建提交、推 ref，全部带回读校验。
   （别用 `git push`，别花时间修代理。）
2. **本机没有 node**，`vps-deploy/_gen_installer.mjs` 跑不了。要改 `deploy-astrbot-page.sh`
   只能定向替换对应 heredoc，并且**必须同步改生成器源码**，否则下次谁跑生成器就覆盖回去了。
3. PowerShell 里写 Python 一行流很容易被引号/`%` 咬到 —— 一律**落成 `.py` 文件再跑**。
   （Python 里格式化 shell 的 `%s` / `%n` 要写成 `%%s` / `%%n`。）
4. **PowerShell 的 `>` 重定向会写 UTF-16、并破坏二进制**。抓截图或拉日志一律用
   `cmd /c "... > 文件"`；看含中文的日志也别直接 `Get-Content`（GBK 乱码），
   用 `adb exec-out run-as com.termux cat <文件> > 本机文件` 再读。
5. **GitHub 内容接口会遇到瞬时 `Remote end closed connection`** —— 重试即可，不必怀疑内容。
6. **`git ls-tree` 默认会把中文路径转义**（`core.quotepath=true`），对账时一律加
   `-c core.quotepath=false`，否则会误判「文件一边有一边没有」。
7. **站点对 `Python-urllib` 的默认 UA 返回 403**。用 python 取站点内容要带
   `User-Agent: Mozilla/5.0`（curl 默认 UA 能过）。
8. **下载页出现 +367 B 不是脚本写的**：那是 Cloudflare 注入的
   `static.cloudflareinsights.com` beacon 脚本，磁盘上的文件没变。
9. 设备上的 `grep`/`sed` 在 houdini 转译下**偶发段错误**（Termux aarch64 程序跑在 x86_64 模拟器上），
   看到 `Segmentation fault` 先怀疑它，别急着怀疑 QQ。同理 `sed` 不吃 `\x1b\[...\]` 这种正则。
10. `run-as com.termux /system/bin/sh` 是**非登录 shell**，`$HOME` 是空的 —— 脚本里一律用绝对路径
    `/data/data/com.termux/files/home/.qqbot`。

## 十二、追加记录：v1.1.19（真机 QQ 秒退）

### 12.1 症状：修完 Xvfb，下一层才露出来

1.1.18 补回 `--link2symlink` 之后，真机上 Xvfb 起来了，但 **QQ 紧接着自己秒退**。
用户给的现场是 `<uid>/grep: <pid>/stat: No such file or directory`，shell 里只有
`Trace/breakpoint trap`，NapCat 照样起不来。

从用户上传的错误报告里读到完整因果链（真机 Redmi 24069RA21C / Android 16 / arm64-v8a /
kernel 6.1.138-android14-11）：

```
GLX is not present
Initialization of all EGL display types failed.
FATAL:sandbox/linux/services/proc_util.cc:114
  Check failed: . : Operation not permitted (1)
GPU process isn't usable. Goodbye.
```

两段因果关系：

1. QQ 的 Chromium 会先起一个 GPU 子进程去初始化 EGL。沙盒的虚拟屏幕（Xvfb）没有 GLX，
   这一步必然失败 —— 但这只让它**退到软件渲染**，本身不致命。
2. 致命的是紧接着那一步：它要枚举那个 GPU 子进程的 `/proc/<pid>/fd` 来校验沙箱，
   而 **Android 10 起 `/proc` 对非本进程大幅收紧**，`fstatat()` 直接返回 EPERM。
   连撞三次之后 `GPU process isn't usable. Goodbye.` 把主进程一起带走。

所以病根不是「没有 GPU」，而是「**有 GPU 子进程**」—— 只要让它别去起那个子进程，
`/proc` 那一步根本不会发生。

## 十三、追加记录：v1.1.20（真病因是 Xvfb 色深）

### 13.1 症状与 1.1.19 一模一样

1.1.19 用 `--disable-gpu` 那一档装上真机，结果还是 `Trace/breakpoint trap`，NapCat 起不来。


关键在最后那条日志的顺序：`--disable-gpu` 并没有阻止 GPU 子进程被拉起来，它只是不让

而且因为「没有软件合成可退」，反而死得更干脆。

### 13.2 真病因：屏幕只有 8 位色深

`XVFB_VARIANTS` 的第一档是 `1x1x8 +extension GLX +render`（1 像素 × 8 位色深），
这是照抄参考项目 AstrBot-Bubble-Android-App 的写法。但 **8 位屏没有可用的 GL 配置**，
ANGLE 必然报 `GLX is not present`。

在模拟器上做了决定性实验（`out/gltest2.sh`）：同一份 rootfs、同一个 QQ、只改 Xvfb 的
`-screen` 参数，各跑一次看日志。

| Xvfb 参数 | 结果 | ANGLE/EGL 报错行数 |
| --- | --- | --- |
| `1x1x8 +extension GLX +render` | GPU 进程崩 | 20 |
| `1x1x8` | GPU 进程崩 | 20 |
| `640x480x16` | GPU 进程崩（`No suitable EGL configs found`） | — |
| `640x480x24` | **正常出二维码** | **0** |
| `1280x800x24` | 正常 | 0 |

所以：**只有 24 位色深能让 GPU 进程初始化成功**，8 位没 GL、16 位配不出 EGL config。
之前两版都栽在这个「照抄来的第一档」上。

顺带澄清一个误导性日志：`sandbox/linux/services/proc_util.cc:114 Check failed: . :
Operation not permitted` 是 GPU 进程**退出时**的清理动作（枚举 `/proc/self/fd`），
是症状不是病因 —— 1.1.19 就是被它带偏，去改 QQ 的启动参数了。

  预构建 rootfs（人家那份 rootfs 自带整套 mesa / GL 模块）。参数和环境是一套的，
  只抄参数就是随机中奖。
- **症状日志会骗人**。`proc_util.cc` 那个 `Operation not permitted` 太像「权限问题」了，
  连着两版都在往「改 QQ 参数、绕沙盒」上使劲。正确做法是：**先做单变量对照实验**
  （只改一个变量，看报错数量变化），再决定改哪儿。这次就是靠一张 5 行的对照表锁定的。
- **模拟器不是完全没用**。判断标准是：这个差异在模拟器上能不能拉开。色深能（同一台
  机器上 8/16/24 位表现不同），`/proc` 规则不能（模拟器就是不复现）。能拉开的差异，
  模拟器实验就是硬证据。

### 15.2 崩溃记录器（`build/opt/qqbot/sandbox/crashwatch.c`，272 行）

- 用 `LD_PRELOAD` 注入 QQ 的每个进程（QQ 主进程、zygote、GPU、worker 都在内）。
- 捕获 `SIGSEGV / SIGABRT / SIGBUS / SIGILL / SIGFPE / SIGTRAP`。
- 落盘内容：信号、`si_code`、出错地址、RIP/RSP/RBP、栈内容、`/proc/self/maps` 里的模块基址、

  否则崩溃处理器自己再崩一次，现场就没了。
- 由 `run-napcat.sh` 首次运行时用设备上的 `g++` 现编成 `/qqbot-cache/crashwatch.so`

### 15.3 `link.sh` 的三档判定

| --- | --- |

| 有新增实例（`need` 非空） | 重启一次（AstrBot 必须多监听一个端口，没有热加载入口） |
| 只有删除实例（`extra` 非空） | **不重启**，只留一个没人连的监听口 |

## 十七、追加记录：v1.1.24（把真机的崩溃现场弄回来）

### 17.1 先确认了一件事：「退出码 11」= SIGSEGV

真机日志里那一行是 `[NapCat] [UtilityProcess] Worker进程退出，退出码: 11`。
它到底是「普通退出码 11」还是「被信号打死」，决定了后面所有排查方向。

做法：在模拟器上找到 NapCat 的 Worker 子进程（`exe --type=utility --utility-sub-type=node.mojom.NodeService`），
`kill -SEGV <pid>`，日志立刻打出：

```
10-19 10:23:57 [error] [NapCat] [UtilityProcess] Worker进程退出，退出码: 11
10-19 10:23:57 [warn]  [NapCat] [UtilityProcess] Worker进程意外退出 (1/3)，正在尝试重新拉起...
```

**一模一样。所以 11 就是 SIGSEGV。**（`Bw = 3`、`O8 = 1e4`：10 秒内崩 3 次，主进程 `process.exit(1)`。）

模拟器崩一次能自己拉起来并正常出二维码；真机是连着崩，所以永远起不来 —— 差别在「崩得多快」，
不在「崩不崩」。

### 17.2 为什么 1.1.22 的崩溃记录器在真机上一份文件都没写

`crashwatch.c` v1 是在 `__attribute__((constructor))` 里装一次 `sigaction`。
但 **Chromium 启动时会自己调 `sigaction()` 把处理器换掉**，等于把我们的顶掉。
于是崩溃全落在 Chromium 的处理器里，我们的代码一次都没被调用 ——
报告里 `crashes/` 一直是空的，不是记录器没编出来（`crashwatch.so` 在、`cw-build.log` 0 字节）。

顺带排除了一个方向：Chromium 自带的 Crashpad 也没用。
`.../qqinst/bot1/.config/QQ/Crashpad/` 里只有一个 `client_id`（36 字节），全盘 `find -name '*.dmp'` 零命中。

### 17.3 改了什么

| 文件 | 改动 |
| --- | --- |
| `build/opt/qqbot/sandbox/crashwatch.c` | **自己导出 `sigaction()`**：应用来装处理器时先记进 `g_app[]`，实际装的是我们的；崩溃时先写现场，再 `chain_to_app()` 把控制权交还给应用原本那个处理器（按 `SA_SIGINFO` 区分 `sa_sigaction` / `sa_handler`），QQ 行为不变。新增 `dump_pc_segment()`：流式解析 `/proc/self/maps`，直接写出「pc 落在哪一段、哪个 .so」。 |
| `build/opt/qqbot/sandbox/run-napcat.sh` | 编译行加 `-ldl`；启动 QQ 前清理 `crashes/`，**只留最近 4 份**；新增 `qq-env.txt` 覆写机制（`/qqbot-cache/qq-env.txt`，一行一个 `KEY=VALUE`），启动行改成 `env "${QE[@]}" LD_PRELOAD=...`。 |

实测（模拟器）：`kill -SEGV` Worker → `crash-57774-sig11.log`（129,121 B），开头就是

```
signal   = 11 (SIGSEGV)
app_hdlr = 1
pc = 0x775de60cd3f7
--- pc 所在段 ---
775de60cd000-775de60ce000 rwxp 0012a000 08:23 3811930 .../usr/lib/x86_64-linux-gnu/libc.so.6
```

`app_hdlr = 1` 就是「Chromium 确实装过自己的处理器、而我们成功接管」的证据。

### 17.4 顺手排除的一条路：单进程模式

`napcat.mjs` 里有个官方开关 `NAPCAT_DISABLE_MULTI_PROCESS=1`，
打开后 `p2e()` 走 `if (Ed.isMultiProcessDisabled) { await NL(); return; }`，
**根本不 fork worker**。看起来像是「绕开那个会崩的子进程」的完美答案。

实测（模拟器，`qq-env.txt` 注入）：worker 进程确实没有了，但 NapCat 在 QQ 主进程里跑到

```
NapCat Shell App Loading...
prepare write and writev hooks
Segmentation fault
```

就崩。**结论：worker 子进程正是 NapCat 用来躲开「在 QQ 主进程里 hook 会崩」的手段**，
关掉多进程只是把崩溃搬进主进程，更糟。所以 `run-napcat.sh` 里默认 `QE=()`，不设任何环境变量，
只把覆写机制留着。

### 17.6 这轮踩的坑

1. **`ps` 里 QQ 的主进程 cmdline 是 `qq --no-sandbox ...`，不是 `/opt/QQ/qq`** ——
   用 `grep 'opt/QQ/qq'` 会一个都匹配不到，误判成「QQ 没起来」。

### 18.2 根因：Worker 走的是 Electron 的 UtilityProcess

日志顺序是关键证据（真机 `qq-bot1.log`，12:17:36 / :37 / :39 连续三轮）：

### 19.2 崩溃地址把范围缩到一个数

1.1.25 的崩溃记录（`report_1319.txt:594-643`）：

| 字段 | 值 |
| --- | --- |
| signal | `11 (SIGSEGV)`，`si_code=1`（SEGV_MAPERR） |
| **si_addr** | **`0x2045d8`**（5 份记录完全一致） |
| pc | `模块基址 + 0x39EE44`（= `gum_elf_module_load+0x880`，指令 `ldr w1,[x20]`） |
| 模块 | `/opt/QQ/resources/app/app_launcher/napcat/native/napi2native/napi2native.linux.arm64.node` |
| maps 头两行 | `00200000-00201000 r--p …/usr/libexec/proot/loader`，下一段映射在 `0x129e6a4000` |

`si_addr` 在 5 次崩溃里恒定、而模块基址每次都不同（ASLR）→ 说明它不是随机指针，而是
`固定基址 + 固定偏移` 算出来的。`0x2045d8 - 0x200000 = 0x45d8`，正好是
Termux proot loader（`$PREFIX/libexec/proot/loader`，18,136 字节）的 **`e_shoff`**
（`out/check_loader_elf.py` 用 pyelftools 读出：`ET_EXEC`、`entry=0x5400000000`、
`e_shoff=0x45d8`、`e_shnum=4`、`e_shentsize=64`）。

### 19.3 机制：proot 只映 loader 的两段，gum 却按 e_shoff 去读节头

loader 只有两个 PT_LOAD：

- `vaddr=0x00200000 off=0x000000 filesz=0x000120 flags=R` → 运行时只占用 `00200000-00201000` 一页；
- `vaddr=0x5400000000 off=0x004000 filesz=0x000468 flags=RX` → `5400000000-5400001000`。

节头表在文件偏移 0x45d8，**两段都没覆盖**。frida-gum 枚举模块时把 `0x200000` 当模块基址、
按 `e_shoff` 去拷节头，于是读到 `0x2045d8` —— 那里没有任何映射，SEGV_MAPERR。
反汇编（capstone，`vaddr 0x39ED00` 起）还能看到守卫逻辑：`ldrh w1,[x28,#0x92]`（`e_shnum`）
`× ldrh w22,[x28,#0x94]`（`e_shentsize`）与 `e_shoff` 相加后 `cmp x20,x1; b.eq` ——
**`e_shnum=0` 时整段拷贝循环直接跳过**，这正是补丁下手的点。拷贝步长 `lsl x3,x2,#6` = 64 字节，
也正好是 `Elf64_Shdr` 的大小。

### 19.4 修法：给 loader 一份「节头清零」的副本

`build/opt/qqbot/common.sh` 在 `export PROOT_TMP_DIR` 之后新增：

- `qq_loader_patched()`：用 `dd … | tr -d '\000'` 判断偏移 0x28 的 8 字节与 0x3C 的 4 字节是否全 NUL；
- `qq_make_loader_fix()`：`cp` 到 `$QQBOT_HOME/proot-loader`、`chmod 755`，再两条
  `dd if=/dev/zero of=… bs=1 seek=40/60 count=8/4 conv=notrunc` 清零 `e_shoff` 与 `e_shnum`+`e_shstrndx`；
- `qq_proot_fix_loader()`：只在用的是 Termux 那份 proot（`$PREFIX/bin/proot`）时生效，
  源文件更新或补丁丢失就重做，然后 `export PROOT_LOADER=…`（顺带 `PROOT_LOADER_32`）；
- `qq_proot_selftest()` 加了自动回退：带补丁自检失败时 `unset PROOT_LOADER` 再试一次，
  成功就删掉补丁文件并提示「loader 补丁与当前 proot 不兼容，已回退」。

为什么清零是安全的：内核执行程序只读 program header，节头表只服务于工具；loader 本身是
`ET_EXEC` 的两段小桩，运行期不会回头读自己的节头。删掉 `PROOT_LOADER` 即可完全回退。

### 19.5 诊断补全

- 「检查运行环境」（`doctor.sh`）新增 `loader补丁:` 一行：已启用（打印 `PROOT_LOADER`）/
  已生成但本次没挂上 / 未启用（打印原 loader 的 `e_shoff` 十六进制）。
- 「上传错误日志」（`upload-log.sh`）新增 `proot loader 补丁` 段：系统 loader 的路径、字节数、
  `e_shoff`，`PROOT_LOADER` 当前值，以及补丁 loader 自己的 `e_shoff`。

### 21.4 「缺少隐私政策」到底是什么（结论）

- **不是 Android 平台机制**：`android.R$attr` 里 "privacy" 命中 0 次（`android:privacyPolicy` 这个属性
  根本不存在，写了 aapt2 会报 unexpected attribute）；Android 16 对侧载的硬门槛只有 targetSdk ≥ 24，
  我们是 28，这一关是过的。
- **是小米 HyperOS 安装器（应用包管理组件）+ 安全中心的风险判定**，命中小米《风险应用审查标准》
  第九类「应用隐私不合规」第 1 条「应用的隐私政策未向用户进行明示」；同包名 `com.termux`、
  调试证书、`debuggable=true`、apktool 重打包、以及 READ_LOGS / DUMP / WRITE_SECURE_SETTINGS /
  MANAGE_EXTERNAL_STORAGE / REQUEST_INSTALL_PACKAGES 等高敏权限，逐条踩着小米生态政策 2.3.6 / 2.3.7。
- **我们能做的都做了**：运行期隐私政策（明示）+ 去掉 `debuggable`（去掉「被重新打包」的显式标记）。
  但**拦截发生在应用运行之前**，由安装器 App 与云端/缓存共同判定，APK 里补隐私政策**不保证解拦**。
- **真机上真正有效的还在安装器侧**（已写进《使用说明》第二、十七节）：
  ①手机管家关「安装监控 / 安装前扫描」、「安全守护」、「应用防护」；
  ②设置 → 应用设置 →「应用包管理组件」卸载更新 + 清除数据 + 联网控制禁止其联网；
  ③断网安装（先清安装器数据）；④电脑 `adb install -r`（完全跳过安装器 UI）。
- **不要做的事**：加 `android:privacyPolicy`（属性不存在）、加 `privacy_policy_url` meta-data（无任何依据）、
  改包名（Termux 硬编码 `/data/data/com.termux`、`sharedUserId`、bootstrap 路径）、
  降 targetSdk（< 24 直接 `INSTALL_FAILED_DEPRECATED_SDK_VERSION`）。

### 21.5 这次踩的坑

1. **去掉 `debuggable` 的副作用**：`adb shell run-as com.termux …` 立刻失效
   （`run-as: package not debuggable: com.termux`）。模拟器上改用 `adb root` 看私有目录；
   真机排障靠「上传错误日志」那条通道。
2. **站内下载 APK 会 403**：站点按 UA 过滤，`urllib` 默认 UA 被拒；要带浏览器 UA + Referer。
3. **`push_api2.py` 读工作区文件算 blob 会卡住**：`.gitattributes` 会在 add 时把 CRLF 归一化成 LF，
   这时工作区字节算出来的 SHA 与 `ls-tree` 的对不上；改成 `git cat-file blob <sha>` 取对象内容。
4. **PowerShell 会把 `git rev-parse "HEAD^{tree}"` 当成 `-encodedCommand`**：`{}` 必须加引号包起来。
5. **改完 index.html 一定要跑静态自检**：`out/chk_html_128.py`（div 配平 / `node --check` / 关键锚点）
   与 `out/chk_apk_129.py`（包内 manifest 无 debuggable、资源里有隐私政策与浏览器文案）。

### 24.1 先定「报错」是什么

```

  Exception in callback BaseSelectorEventLoop._accept_connection
  File ".../asyncio/selector_events.py", line 178
  File ".../socket.py", line 295, in accept
```

## 二十六、追加记录：v1.1.35（实例删不干净 —— 幽灵实例卡）

### 26.1 由来

用户报障：「软件的 napcat 的实例添减有问题，自带的一个实例删了之后，
主页它不显示删掉，它还是显示在」。即：实例已经删了，主页那张卡还在，
点进去还能看到它，点删除也没反应 —— 一张删不掉的幽灵卡。

### 26.2 根因（两处叠加，缺一不可）

1. **原生侧不写空表**。`ui/src/com/termux/qqbot/InstancesState.java` 的 `update()}`
   写盘条件是 `if (out.length() > 0 && !out.toString().equals(cur.toString()))`。
   删掉**最后一个**实例时序列化结果就是空表，`out.length() > 0` 为假 →
   **永远不写盘**，`state/instances.json` 里那条旧记录一直留着。
   只要还剩一个实例，条件成立，所以这个 bug 只在「删到零个」时暴露。
2. **前端把 instances.json 的键也当实例**。`index.html` 的 `renderInst()` 是把
   「bots.json 的实例 ∪ instances.json 的键」并起来渲染的：

   ```js
   for (k in map){ if (Object.prototype.hasOwnProperty.call(map, k) && !seen[k]){ ids.push(k); seen[k] = 1; } }
   ```

   于是残留键渲染成一张完整实例卡 —— 而它并不在 bots.json 里，
   走删除流程时原生找不到这个实例，删了等于没删。

### 26.3 修复

- `InstancesState.java`：写盘条件移进 `if (arr != null)` 内、去掉 `out.length() > 0`。
  即「bots.json 读得到就照实写（含空表）」，读不到才跳过 —— 避免把「读不到」
  当成「没有实例」，反过来把状态抹掉。
- `renderInst()`：实例 id **只来自 `validBots(S.bots.bots)`**；
  `instances.json` 只用来补 `started / lastOffline / uin / nick / alive` 这些运行时字段。
- `doDelBot(id)`：删后立刻从内存 `ext().inst.map` 里摘掉并重绘，
  不等原生开 proot 跑完删除脚本（`removeBot` 是异步的，十几秒到一分钟）。
- `paintHero()`：新增 `botCount(st)`，分支顺序里插在 `!installed` 之后 ——
  没实例时 hero 显示「还没有实例」，不再说「一切正常」。
  `botCount` 读不到 bots 时返回 1（宁可不说，也别误报）。
- 顺手：`renderBots` 展开区原来**无条件**给「设为当前」，当前实例也有，
  点了只会把容器重启一次、白掉一次线 → 改成 `if (!act)`；
  实例卡离线文案原来是「在线 未运行」自相矛盾 → 改成 `esc(alive ? ("在线 " + upTxt) : "未运行")`。

### 29.2 两个决策（ask_user_question 已确认）

| 决策 | 选项 | 理由 |
| --- | --- | --- |
| 内置范围 | **全内置**（APK 约 650 MB） | 彻底摆脱对 apt / pip / QQ 下载地址的依赖 |
| 架构 | **构建时选架构，出两个包** | 一个包塞两套镜像要 1.2 GB；分开发，真机拿 arm64、模拟器拿 amd64 |

### 29.3 载荷是怎么来的

**amd64（模拟器）**：直接在 MuMu 里那套已部署好的沙盒上裁剪 —— 删 `var/cache/apt/archives`、`root/.cache/{uv,pip,mesa_shader_cache}`、
`var/lib/apt/lists`、日志，2.9 GB 降到 2.2 GB；`tar --exclude=./dev ./proc ./sys ./run ./tmp … | xz -6 -T0`，约 9 分钟出包，
**604,245,316 B**（压前 2.25 GB，比例 0.258，68,330 个条目）。

**arm64（真机）**：本机跑不了 arm64，qemu 路线也没走通（`qemu-user-static_*_amd64.deb` 在 tuna / ustc / ftp.debian.org 全部 404），
改成**交叉下载 + 解包拼树**：

- `dpkg --add-architecture arm64`，源必须按架构限定（`[arch=amd64] …/ubuntu`、`[arch=arm64] …/ubuntu-ports`），否则 apt 全 404；
- `apt-get download <pkg>:arm64` 取 **360 个 deb（310 arm64 + 50 arch:all）**。中途踩过一个坑：脚本里 `apt-get download "$p"` 的
  fallback 会在 `$p:arm64` 失败时**静默下 amd64 包**，结果 361 个 deb 里 222 个是 amd64、`libc6` 根本没有 arm64 版；
- `dpkg-deb -x` 在 proot 里不可用（`Cannot mkdir` / `Invalid cross-device link`），改走 `dpkg-deb --fsys-tarfile` 转普通 tar，
  再到 Termux 侧用原生 tar 解包 → `extracted=360 failed=0`；
- QQ arm64：`linuxqq_3.2.34-53644_arm64.deb`（207,538,924 B）同样转 tar 再解 → `/opt/QQ` 645 M；
- NapCat 纯 JS，直接从 amd64 树拷；AstrBot 的 venv 用 `pip download --platform manylinux2014/2_17/2_28_aarch64` 取 **144 个 wheel**，
  只有 `aiocqhttp`、`jieba` 两个纯 Python 包从 amd64 树复用；
- 手工解包不会建 merged-usr 链接，`/lib` 会是真目录、`/lib/ld-linux-aarch64.so.1` 缺失 → 归一脚本把 `bin/sbin/lib` 并进 `usr/*`
  再换成符号链接，并补上加载器链接；
- 逐个校验 ELF `e_machine`（`od -An -tx1 -j18 -N2`，`b700` = AArch64）：`usr/bin/bash`、`usr/bin/python3.12`、`opt/QQ/qq`、
  numpy 的 `.so` 全部正确，`x86_64 leftovers: 0`；

**583,010,488 B**（压前 2,351,134,720）。

两个包都写了 `.qqbot-bundle` 清单（`30-apt 40-qq 50-napcat 60-astrbot`），部署时据此把这几步直接标成完成。

### 29.4 真正踩到的六个坑

1. **内置包解压成功又被删掉重建**（最贵的一个）：`steps/20-rootfs.sh` 的内置包分支解压完没有 `exit 0`，代码继续往下走进在线分支，
   而在线分支第一件事就是 `rm -rf "$ROOTFS"` —— 2.2 GB 的树瞬间变回 84 MB 的空壳，可 30~60 步的「已完成」戳还在，
   于是全跳过，最后卡在 `65-link` 的 `python3: command not found`。日志铁证是连续四行：`内置包已解压` → `已补齐运行时目录` →
   `内置包已包含的步骤已标记完成` → **`解压 rootfs 到 …`**。补 `mkdir dev/proc/sys/run/tmp/opt` + `chmod 1777 tmp` + `exit 0`。
2. **`--link2symlink` 标记是粘性的**：`common.sh` 的文件系统体检通过后只删探测文件、不撤标记，之后每次进 proot 都把 `link()`
   模拟成符号链接，留下 `var/lib/dpkg/status -> .l2s.status0001` 这类悬空链。换台设备后 dpkg 报
   `Operation not permitted`，自愈逻辑又判「文件系统不支持硬链接」把整棵树删了重建 —— 假象套假象。体检通过即 `rm -f link2symlink`。
3. **权限没归一**：树是在 Android 的 proot 里建的，tar 原样记下 135 个 `drwx------`、105 个 `-rw-------`、16 个 `-rwx------`
   （来自 `/data/data` 本身）。换设备换 uid 就 lstat EPERM。打包前统一 755 / 644（`shadow`/`gshadow` 640、`/root` 700、`/tmp` 1777）。
4. **`tar -xJf` 在 Termux 上不可靠**：不是不支持 xz，而是它按名字 exec `xz`，PATH 里没有就 `Cannot exec`。
   改成 `"$PREFIX/bin/xz" -dc "$BUNDLE" | tar -xf -`，并加 `set -o pipefail` —— 否则 xz 中途死掉时 tar 读到空流返回 0，失败会被当成功。
5. **d8 不能处理匿名内部类**：`kickBundleCopy` 里直接 `new Thread(new Runnable(){…})`，d8 抛
   `NullPointerException: Cannot invoke "String.length()"` / `Compilation failed with an internal error`。
   仓库里 `BgTask.java` 的头注释早写着这件事（「d8 处理匿名内部类会崩，所以这里必须是具名顶层类」），新建 `BundleCopyTask` 即可。
6. **构建脚本的通配删除**：`Get-ChildItem AstrBot-*.apk | Remove-Item` 会连另一个架构的包一起删掉（实际发生过一次，arm64 包被删）。
   改成按架构拼名、只删自己要写的那个文件。

### 32.3 顺带修：Android 13+ 新装后通知根本不出现

### 35.2 真因一：second-stage 脚本的前缀没跟着改

`termux-bootstrap-second-stage.sh` 里 `TERMUX_PREFIX` 与 `dpkg` 的 admindir 仍写死 `/data/data/com.termux/files/usr`。包名改成 `zhuxin.astrbot` 后第二阶段执行 `*.postinst` 必然失败，`TermuxInstaller` 见非 0 就把 `usr/` 清空，界面上只看到「Unable to install bootstrap」。

修法（`tools/reloc_bootstrap.py`）：**先 `patch_text` 再 `patch_stage2`**。原先 elif 分支只调了 `patch_stage2`，脚本本体里的 5 处 `com.termux` 原封不动；现在整份脚本按新前缀重写，并在第 2 行插入日志重定向（`$HOME/.qqbot/logs/second-stage.log`），下次真机失败能直接拿到完整输出。

### 35.3 真因二：lief 给 32 个 ELF 新增了 PT_LOAD 段

上一版用 lief 改 RUNPATH。字符串变长时 lief 会重建程序头表——`bin/apt` 从 11 段变 12 段、`lib/libiconv.so` 10→11、`lib/liblz4.so`、`lib/libxxhash.so.0.8.3`、`libexec/coreutils/libstdbuf.so` 等共 32 个文件（`out/_phcmp3.py` 逐项比对 pristine / reloc 得出）。MuMu（ARM 转译）能跑，但真机 Android 16 的 linker 直接 `execve` 失败，表现就是 `dpkg` 起不来 → second stage 非 0 → 同一个弹框。

修法：**原地等长改写**。长前缀缩成短别名——`/data/data/<pkg>/files/usr` → `/data/data/<pkg>/u`（短 3 字节）、`/data/data/<pkg>/files/home` → `/data/data/<pkg>/h`；替换必须写成**一次** `out[i:end] = newstr + b"\x00"*pad`，分两次切片赋值会把 bytearray 改短（曾让 `bin/bash` 从 837,728 掉到 837,675，报 `invalid shdr offset/size: 836192/1536`）。别名由新增的 `PrefixAlias.java`（package `com.termux.app`）在 Activity / GuardService / Shell 三处入口建符号链接：`files/u -> files/usr`、`files/h -> files/home`。

.so 的夹心结构必须原样保留：[0,1328) ELF 头 + 程序头、[1328,EOCD) ZIP、EOCD 后 2,761 B 动态段、`shoff=29391584` 的节头表到 EOF。输出 = 头 + 新 ZIP + NUL 填充 + **pristine 的尾部**，总长恒为 29,392,992 B。砍掉尾部会报 `dlopen failed: ... has invalid shdr offset/size`。

## 三十六、追加记录：v1.2.4 —— proot 缺 loader 的两个修法与清单再收权限

### 36.1 起因

VPS 错误日志 `/data/astrbot-errlogs/20261022-081149-15020.txt`：Redmi 24069RA21C / Android 16（sdk 36）/ arm64。第 1 步 `10-termux` 的 proot 自检连续三次失败，日志里是：

```
proot error: execve("/system/bin/sh"): No such file or directory
the loader was not found or doesn't work
```

`deploy.error=proot 自检失败`。连第 1 步都没过去，不是镜像、不是 QQ，也不是手机权限问题。

### 36.2 根因

打包时只带了 proot 本体，没带 `libexec/proot/loader` 与 `loader32`。proot 的 loader 路径是编译期写死的：它要在 guest 里执行 `/system/bin/sh` 时，先加载 `$PREFIX/libexec/proot/loader`，文件不存在就报 `execve("/system/bin/sh"): No such file or directory`，随后补一句 `the loader was not found or doesn't work`。

x86_64 模拟器没暴露这个问题：amd64 走随包的静态 `proot-x86_64`，它的 loader 是编进本体里的，不依赖 `libexec/proot/`。所以 1.2.3 在 MuMu 上八步全绿，到 arm64 真机第 1 步必挂。

### 36.3 修法（两份 loader，两个去处）

- `build/libexec/proot/loader`、`build/libexec/proot/loader32`：两个 ELF 随 `build/` 一起进 `libtermux-bootstrap.so` 的内嵌 ZIP，全新安装时由 `TermuxInstaller` 解到 `$PREFIX/libexec/proot/`。加这两个文件后 `.so` 总长仍是 **29,392,992 字节**（空间靠 `--drop` 腾）。
- `build/opt/qqbot/libexec/proot/loader`、`loader32`：同一对文件再放一份，随 `build/opt/qqbot/**` 打进 `assets/qqbot-scripts.zip`，落到 `$PREFIX/opt/qqbot/libexec/proot/`，专门给覆盖升级兜底。
- `steps/10-termux.sh` 在 proot 自检之前补装：判断 loader 是否存在用 `-f` 而不是 `-x`（同步下来的文件权限是 644，`-x` 会把存在的文件误判成不能用），存在就 `cp -f` 到 `$PREFIX/libexec/proot/` 并 `chmod 755`，`loader32` 同样处理；补不上会 `qqwarn` 打警告。

### 36.4 覆盖升级的兜底链路

`TermuxInstaller` 只在 `files/usr` 不存在时才解包 `libtermux-bootstrap.so`，已装 1.2.3 的设备覆盖升级到 1.2.4 不会重新解包，新加的 `build/libexec/proot/` 自然拿不到。兜底链路是：

1. 应用启动时把 `assets/qqbot-scripts.zip` 解到 `$PREFIX/opt/qqbot/`（含 `libexec/proot/loader`、`loader32`，解出来是 644）；
2. 点「开始部署」进入第 1 步 `10-termux`，脚本发现 `$PREFIX/libexec/proot/loader` 缺失，就从 `$PREFIX/opt/qqbot/libexec/proot/` 复制并 `chmod 755`；
3. 再跑 proot 自检，三次全过才继续第 2 步。

所以升级路径是：**1.2.3 → 1.2.4 直接覆盖安装，装完打开应用，第 1 步自动补 proot loader，再点「开始部署」即可**；沙盒、QQ 登录态与配置都保留。

### 36.5 清单再收两条权限与三处不能动的保留项

- 删掉 `REQUEST_INSTALL_PACKAGES` 与 `WRITE_EXTERNAL_STORAGE`。应用内更新是交给系统浏览器下载，不需要装包权限；写外部存储的代码路径也早已没有。清单现在只剩 8 条：INTERNET、ACCESS_NETWORK_STATE、FOREGROUND_SERVICE、WAKE_LOCK、VIBRATE、REQUEST_IGNORE_BATTERY_OPTIMIZATIONS、RECEIVE_BOOT_COMPLETED、POST_NOTIFICATIONS。
- `RunCommandService` 仍 `android:exported="false"`。
- `android:sharedUserId` 保留：实测把它删掉后，已装 1.2.3 的机器覆盖安装报 `INSTALL_FAILED_UID_CHANGED`，只能卸载重装（沙盒数据一起没）。
- `TermuxDocumentsProvider`、`TermuxOpenReceiver$ContentProvider` 必须保持 `android:exported="true"`：实测改成 `false` 后应用启动即崩，logcat 里是 `SecurityException: Provider must be exported`。

## 三十七、追加记录：v1.2.5 —— 首次部署改回官方镜像源

### 37.1 起因

用户反馈原话：「从服务器下载的速度好慢啊 还是走官方源吧」。实测从站内 `/dl/` 拉 604 MB 整包镜像，速度只有 140~200 KB/s，整包要三四十分钟；同一时间官方镜像站（清华 / 中科大 / 阿里）的 apt 能跑到 3~5 MB/s。瓶颈在站点带宽，不是用户网络。

### 37.2 改法

- `build/opt/qqbot/steps/20-rootfs.sh`：`qq_bundle_pull` 从默认先试整包改成只有 `QQBOT_BUNDLE=1` 才走；默认分支打印「走官方镜像在线安装（清华 / 中科大 / 阿里源），不需要下整包镜像」，直接进入 `30-apt` 在线装依赖。
- `build/opt/qqbot/common.sh`：更新 `QQBOT_CDN` 注释，写明只有整包镜像模式才用得到，部署前 `export QQBOT_BUNDLE=1` 才会去下 604 MB 镜像，默认走官方镜像在线安装。
- 整包镜像没删：站点 `/dl/` 下 `bundle-arm64.tar.xz` / `bundle-amd64.tar.xz` 继续留着，离线 / 内网 / 镜像站不可用时设 `QQBOT_BUNDLE=1` 即可。

### 37.3 实测

MuMu 测试机 `pm clear` 后全新安装 1.2.5（未设 `QQBOT_BUNDLE`）：`10-termux` 与 `20-rootfs` 合计约 2 分钟；`30-apt` 从 `mirrors.tuna.tsinghua.edu.cn` 拉到 3~5 MB/s，178 MB 依赖约 1 分钟下完。

### 37.4 界面与站点文案同步

- `ui/assets/qqbot/index.html` 三处：主页部署提示改成「从官方镜像（清华 / 中科大 / 阿里）在线安装运行环境，视网速通常 10~30 分钟」；部署进度面板第 2 步说明改成「下载 Ubuntu 基础系统并解压，1~3 分钟」；「存储占用」里的精简包说明同步改成在线安装。
- `vps-deploy/astrbot_download_sync.py` 两处：下载卡描述与「打开应用，等它自动部署」步骤说明，都从「本站下载约 600 MB 镜像、5~20 分钟」改成「官方镜像站在线安装、10~30 分钟」。

这一版同时出了 arm64 / amd64 两个包，逐条比对 **724 个条目**，只有 `assets/qqbot-scripts.zip` 的时间戳不同，其余内容完全相同 —— 架构是运行时按设备 ABI 选镜像，跟安装包无关。两个包一样就没必要让用户选架构，合并成一个 `AstrBot-1.2.5-arm64.apk`，模拟器也能直接装。
