## 2. A —— 前端运行时开销

### 2.1 四个 `setInterval` 里各自做了什么

`index.html` 全文共 4 处 `setInterval`、26 处 `setTimeout`、120 处 `el()`、95 处 `Android.*` 引用。

**① `index.html:2065-2067`（2000 ms，日志页）**
``
setInterval(function(){
  if (S.auto && !document.hidden && el("tab-logs").classList.contains("on")) { loadLog(); loadDuo(); }
}, 2000);
``
- `loadLog()`（`index.html:1578-1589`）：读 `el("logSel").value` → `Android.readLog(name, 400)`（400 行）→ `cleanLog()` → **无条件** `box.textContent = t`（`index.html:1587`）。
- `loadDuo()`（`index.html:1611-1621`）：`napLogName()` → `Android.readLog(n, 200)` **和** `Android.readLog("astrbot.log", 200)`，两次独立桥调用，走 `setPre()`。

**② `index.html:2070-2075`（10000 ms，日志页）**：`fillQrSelect()`（实例数变化时）+ `loadQr()`（1 次 `Android.qr(id)`）。源码注释 `index.html:2069` 已说明「二维码变化不快，10 秒刷一次就够」——这一条设计是对的。

**③ `index.html:2077-2079`（2000 ms，首页）**：`refreshDeploy()`（`index.html:1156-1179`）→ 1 次 `Android.deployInfo()` + `JSON.parse` + 重写 `stepList`（8 个步骤 div 拼串）。

**④ `index.html:2087`（4000 ms，全页面）**：`refresh()`（`index.html:1082-1142`）→ 1 次 `Android.state()` + `JSON.parse` + 约 20 处 `textContent`/`className` + `setHtml(el("pills"), ...)` + 7 个子渲染（`renderBots / renderHomeBots / renderSvc / fillLogSelect / syncAstrPortInput / renderPorts`）+ `refreshDeploy()` + `autoLink()`。

另有 `index.html:2090-2095` 的 `visibilitychange`：回到前台时**一次性**跑 `refresh() + loadLog() + loadDuo() + loadQr() + refreshDeploy()`，即 5 次桥调用突发。

### 2.2 每秒跨语言（JS↔Java）调用次数 —— 实测统计

页面默认停在首页（`index.html:498` `<section class="tab on" id="tab-home">`）。

**场景 A：停在首页（稳态）**

| 桥方法 | 频率 | 说明 |
|---|---|---|
| `deployInfo()` | 0.75 次/秒 | 2 s 定时器 0.5 次/秒 **+** 4 s `refresh()` 内嵌 0.25 次/秒 |
| `state()` | 0.25 次/秒 | 仅 `index.html:2087` |
| **合计** | **1.00 次/秒** | |

**场景 B：停在日志页（稳态）**

| 桥方法 | 频率 |
|---|---|
| `readLog()` | 1.50 次/秒（每 2 s 三次：400 行 + 200 行 + 200 行） |
| `state()` | 0.25 次/秒 |
| `deployInfo()` | 0.25 次/秒 |
| `qr()` | 0.10 次/秒 |
| **合计** | **2.10 次/秒** |

**场景 C：停在首页 + 部署进行中**：`deployInfo` 仍是 0.75 次/秒，但每次都在读正在增长的 `deploy.log`，最坏每次 256 KB → **约 192 KB/秒的磁盘读取**。

> 换算成「天」的量级：日志页常驻一天 = 2.1 × 86400 ≈ **18.1 万次跨语言调用/天**；日志文本约 400 行/秒 → **约 3456 万行/天**跨越 JS↔Java 边界。

### 2.3 重复劳动清单（现象 → 证据 → 改法 → 收益 → 风险）

#### A-1 `refreshDeploy()` 被重复调用（最高性价比）

- **现象**：首页打开时 `refreshDeploy()` 每 4 秒实际执行 **3 次**。
- **证据**：`index.html:2077-2079` 的 2 秒定时器调用 2 次；`refresh()` 在 `index.html:1140` 又调用 1 次，而 `refresh()` 自己由 `index.html:2087` 每 4 秒触发。两者互不知道对方。
- **改法**：给 `refreshDeploy()` 加 1.5 秒节流（记录 `lastDeployFetch` 时间戳，距离上次不足 1500 ms 直接 return），或干脆删掉 `index.html:2077-2079` 整个定时器——因为 `refresh()` 里已经有了一次。部署期想更灵敏反而应该缩短 `refresh()` 的周期。
- **收益**：首页跨语言调用 1.00 → 0.50 次/秒；`deployInfo()` 相关的 stat 从 30 次/4 秒降到 10 次/4 秒；磁盘读 192 KB/秒 → 64 KB/秒。
- **风险**：几乎为零。唯一影响是部署进度条刷新粒度从 0.5 s 变 1.5 s（用户感知不到）。

#### A-2 同一份 QQ 日志每 2 秒被读两遍

- **现象**：`qq-<active>.log` 每 2 秒被读 400 行（大框）+ 200 行（双栏框）。
- **证据**：`index.html:1582` `Android.readLog(name, 400)`，其中 `name = el("logSel").value`（`index.html:1579`）；`index.html:1612-1615` `var n = napLogName(); ... Android.readLog(n, 200)`。`napLogName()`（`index.html:1592-1598`）返回 `"qq-" + S.bots.active + ".log"`，在单实例场景下这正是 `logSel` 里选中的那一个。两者是同一个文件、同一个窗口，只是行数不同。
- **改法**：让 `loadDuo()` 复用 `loadLog()` 刚取到的文本（存到 `S.lastQqText`），只对 `astrbot.log` 发第二次 `readLog`。或者干脆合并成一个 `Java` 方法 `logs(int napLines, int astrLines)` 一次返回两份，把 3 次桥调用压成 1 次。
- **收益**：跨语言文本 400 行/秒 → 267 行/秒；桥调用 1.5 → 1.0 次/秒；`cleanLog` 的正则处理量 -33%。
- **风险**：低。`logSel` 可能被用户手动切到别的文件（如 `supervisor.log`），此时两个框本来就该显示不同内容 —— 复用前要判断 `n === el("logSel").value`。

#### A-3 `loadLog()` 没有去抖，`loadDuo()` 有

- **现象**：`loadLog()` 每次无条件重写 400 行文本；`setPre()` 却有内容比较短路。
- **证据**：`index.html:1587` `box.textContent = t;`（无判断）；对比 `index.html:1604` `if (box.textContent === txt) return;`。
- **改法**：把 `index.html:1604` 那句去抖搬到 `loadLog()` 里；`loadLog()` 与 `setPre()` 合并成一个函数。
- **收益**：日志内容不变的那些轮次（绝大多数）完全不触碰 DOM，省掉一次约 48 KB 文本节点的替换 + 强制重排 + 滚动区重绘。粗估日志页绘制耗时 -50%~-70%（**估算**，未在设备上量帧率）。
- **风险**：低。注意 `loadLog()` 还负责 `atBottom` 自动滚底（`index.html:1586-1588`），去抖路径里要保持这个行为。

#### A-4 `refresh()` 里 7 个子渲染的代价

- **现象**：每次 `refresh()` 都要跑 `renderBots / renderHomeBots / renderSvc / fillLogSelect / syncAstrPortInput / renderPorts / autoLink`。
- **证据**：`index.html:1134-1141`。
- **好消息**：这些渲染最终都走 `setHtml()`（`index.html:1271-1276`），它内部有 `if (node._lastHtml === html) return;` 短路，所以**DOM 不会真的整块重写**（注释 `index.html:1269-1270` 解释了原因：4 秒一次整体重写会让点击落在替换瞬间、`touchend` 不再触发 `click`）。`renderPorts()` 还额外有 `activeElement` 保护（`index.html:1820-1822`）。
- **真正剩余的成本**：每轮仍要**拼出完整 HTML 字符串**再比较 —— `renderBots`（`index.html:1242-1267`，每实例约 12 行含 5 个按钮）、`renderHomeBots`（`index.html:1332-1363`，每实例约 16 行含 6~7 个按钮）、`fillLogSelect`（`index.html:1214-1226`，每 4 秒重建 option 列表）、`renderPorts`（`index.html:1817-1836`）。单实例约 1~2 KB 字符串拼接/秒，多实例线性增长。
- **改法**：给这些函数也加「输入指纹」短路（例如 `renderBots` 先比 `JSON.stringify(S.bots)` 与上次的指纹），字符串都不拼。
- **收益**：稳态下每 4 秒省掉约 1~2 KB 的字符串拼接（CPU 层面很小，但能避免 GC 抖动）。
- **风险**：低，但属于「可做可不做」——**这条不是瓶颈**，真正的瓶颈是 A-1 与 A-2。

#### A-5 代理测速会冻结整个 JS 线程最多 20 秒

- **现象**：设置页「测试代理」点击后页面完全失去响应。
- **证据**：`Android.exec(cmd)` 是**同步阻塞**调用，`index.html:2029-2057` `doTestProxy()` 里调用它；源码注释 `index.html:2020-2022` 已明确写「exec 是同步阻塞调用，WebView 的 JS 线程会被卡住直到 curl 返回」。
- **改法**：把 `Android.exec` 改成异步（Java 侧已有 `runBg(cmd, done, timeoutSec)` 机制，`QqbotBridge.java:16` + `BgTask.java`），结果通过 `Android.onBgDone(...)` 回吐。
- **收益**：消除单点 20 秒冻屏。它不常发生，但一旦发生体验极差（用户会以为 App 崩了）。
- **风险**：中。`exec` 目前共 3 处使用（`index.html` 内），其中 `autoLink()`（`index.html:1151`）是后台语义、改异步反而更对；`doReinstall()`（`index.html:1783`）需要确认是否依赖同步返回。

### 2.4 JSON 与 DOM 的定量

- `JSON.parse` 全文 7 处，其中**热路径 3 处**：`index.html:1084`（`state()`）、`index.html:1158`（`deployInfo()`）、`index.html:1640`（`qr()`）。按 2.2 的频率算，首页稳态 **1 次/秒**，日志页稳态 **0.6 次/秒** —— 绝对值不高，**不是瓶颈**。
- `innerHTML` 赋值全文只有 1 处（就在 `setHtml()` 里），说明 DOM 写入已经被收敛得很干净。
- `textContent` 赋值 40 处，其中真正写入大量文本的是 `loadLog()`（400 行）与 `setPre()`（200 行 ×2）。
- 全部 `el()` 走 `document.getElementById`（`index.html:942`），**没有缓存**：`refresh()` 一次就调 `el()` 约 20 次以上，4 秒一轮。`document.getElementById` 本身是哈希查找（微秒级），**不是瓶颈**，但如果顺手可以加一个 `id→node` 缓存表。

**A 题结论**：前端的开销**不在 DOM、不在 JSON**，而在**两个重复的轮询**（A-1 的 `refreshDeploy` 三连击、A-2 的同一日志读两遍）以及**每次桥调用都携带的最大 256 KB 文件读**。修 A-1 + A-2 + A-4（去抖）即可把前端的跨语言压力砍掉约 60%。

## 3. B —— Android 侧开销

### 3.1 `state()` 单次调用的完整代价分解

`QqbotBridge.state()` 位于 `ui/src/com/termux/qqbot/QqbotBridge.java:26-100`。逐行拆解：

| 行 | 代码 | 实际系统开销 |
|---|---|---|
| `:30-31` | `usrDir().getAbsolutePath()` / `homeDir()` | 纯字符串，0 syscall |
| `:32` | `new File(qqbotDir(),"deploy.done").isFile()` | 1 次 stat |
| `:33` | `pidAlive(supervisor.pid)` → `QqbotActivity.java:285-297` | 1 stat + open/read/close（3）+ `new File("/proc/"+pid).exists()`（1 stat）= **约 5 syscall + 1 次文件读** |
| `:37` | `act.astrbotPort()` → `QqbotActivity.java:603-606` → `astrbotPortRaw()` `:593-600` → `new JSONObject(readBots())` | **第 1 次读 bots.json + 2 次 JSON 解析**（`readBots()` 在 `:540` 已经 `new JSONObject(s)` 校验过一次，调用方又解析一次） |
| `:39` | `act.portOpen(ap)` | **socket #1**（失败路径最多 400 ms） |
| `:40` | `act.astrbotPortRaw() == 0` | **第 2 次读 bots.json + 2 次 JSON 解析** |
| `:43-44` | `svcOff("napcat") / svcOff("astrbot")` → `QqbotActivity.java:428-430` | 2 次 stat |
| `:45` | `act.lanIp()` → `QqbotActivity.java:313-335` | `NetworkInterface.getNetworkInterfaces()` 遍历全部网卡与地址，**约 20~60 syscall** |
| `:47` | `new JSONObject(act.readBots())` | **第 3 次读 bots.json + 2 次 JSON 解析** |
| `:62` | `b.put("up", act.portOpen(bp))` | **每个实例 1 个 socket** |
| `:72` | `act.portOpen(napPort)` | **socket**；而 `napPort` 就是活动实例的 `bp`（`:63-64`）→ **与 :62 重复探测同一个端口** |
| `:73` | `act.portOpen(onePort)` | **socket** |
| `:79-94` | 两个日志目录各 `listFiles()` + 逐文件 `isFile()/length()/lastModified()` | 2 次目录列举 + 每文件 3 次 stat（6 个日志文件 ≈ 18 stat） |

**单实例（稳态）合计**：
- **读 `bots.json` 3 次**，**JSON 解析 6 次**（每次 readBots 内部 1 次校验 + 调用方 1 次）
- **socket connect 4 次**（`astrbotUp`、实例 `up`、`napcatUp`、`onebotUp`），其中第 2、3 次探测的是**同一个端口**
- 目录列举 2 次、stat 约 30 次、网卡枚举 1 次
- **总 syscall 量级约 90~120 次/调用**

**最坏情况（服务全停，端口全不通）**：4 次 `portOpen` 各自耗尽 `QqbotActivity.java:303` 的 `400` ms 超时 = **1.6 秒**。而 `refresh()` 每 4 秒一次 → **WebView 的 JS 线程有 40% 的时间被阻塞**。这正是「部署前/停服后界面发木」的根因。

#### 改法（按性价比排序）

1. **合并 `readBots()`**：`QqbotBridge.java:37` 已经拿到 `ap`，`:40` 的 `astrbotPortAuto` 完全可以用同一个 `readBots()` 结果算出来；`:47` 再解析一次纯粹是重复。**一次 state() 只需要读 1 次 `bots.json`**。收益：-2 次文件读、-4 次 JSON 解析。风险：低（`astrbotPortRaw()` 保持 public 不动，只在 state() 内部换成局部变量）。
2. **端口探测合并 + 缓存**：`:62` 与 `:72` 重复，直接复用；再给 `portOpen` 套一个「同一端口 1.5 秒内不重复探测」的缓存（进程内 `HashMap<Integer,long/boolean>`）。收益：稳态 4 → 2 次 connect，最坏阻塞 1.6 s → 0.8 s。风险：低，缓存窗口要小于轮询周期的一半以上。
3. **缩短 `portOpen` 超时**：`QqbotActivity.java:303` 的 400 ms 对 **本机 loopback** 是极其宽松的 —— loopback 的 connect 要么立刻成功（服务在听），要么立刻 `ECONNREFUSED`。400 ms 只在极端的 CPU 饱和下才有意义。**改成 120~150 ms**。收益：最坏阻塞 1.6 s → 0.6 s。风险：低；建议保留 150 ms 以容忍 proot 下服务的 accept 队列慢。
4. **`lanIp()` 缓存**：`QqbotActivity.java:313-335` 每 4 秒枚举一次全部网卡。局域网 IP 变化只跟 WiFi 上下线有关，**缓存 30 秒**或监听 `ConnectivityManager` 广播即可。收益：每 4 秒省一次网卡枚举（约 20~60 syscall）。风险：低（切换网络后最坏 30 秒内显示旧 IP；`refresh()` 的显示只是给人看的）。

### 3.2 `tail()` —— 隐藏最深的放大因子

`ui/src/com/termux/qqbot/QqbotActivity.java:385-402`：
``
public String tail(File f, int maxLines) {
    ...
    long len = raf.length();
    long chunk = Math.min(len, 262144L);   // ← 固定 256 KB
    long start = len - chunk;
    raf.seek(start);
    byte[] buf = new byte[(int) chunk];
    raf.readFully(buf);
    String text = new String(buf, "UTF-8");
    ...
``

**每次调用都最多读取 256 KB 的字节、分配 256 KB 的 `byte[]`、再构造一个最多 256 KB 的 `String`，最后只截取 14 行或 200 行。**

放大倍率测算（按平均每行 120 字节）：
- `deployInfo()`（`QqbotBridge.java:133`，只要 14 行 ≈ 1.7 KB）：最坏放大 **约 150 倍**
- `readLog(n, 200)`（约 24 KB）：最坏放大 **约 11 倍**

而这些调用在首页稳态下每秒发生 1 次、日志页每秒 1.5 次。**首页稳态的磁盘读量最坏 192 KB/秒、日志页 384 KB/秒**（含 `deployInfo`），全部发生在 JS 桥线程上，每次都要分配 256 KB 的临时数组 —— 这会制造持续的 GC 压力。

**改法**：把固定 `chunk` 改成按需上限，例如 `long chunk = Math.min(len, Math.max(8192L, (long) maxLines * 512L + 4096L));`，并保留原有的「start > 0 时丢掉首个不完整行」逻辑（`:397-400`）。
- 收益：`deployInfo` 单次读盘 256 KB → 约 11 KB（**-96%**）；`readLog` 单次 256 KB → 约 106 KB。整体桥线程磁盘读量降低 **约 60%~90%**。
- 风险：**中**。512 字节/行 是经验值，日志里有超长行（如 NapCat 的 base64 或 JSON 打印）时可能被截断。缓解：`maxLines` 超出后仍按换行切，最坏只是显示不完整；不会漏文件、不会崩。建议先按 `maxLines * 1024` 取，保守一点。

### 3.3 线程模型：IO 到底在哪个线程

- `@JavascriptInterface` 方法由 **WebView 的 JS 桥线程**调用，**不在主线程**（`QqbotBridge.java` 全类没有 `runOnUiThread`）。所以不存在 IO 卡主线程导致 ANR 的问题。
- 但它**阻塞 JS 线程本身**：`Android.state()` 返回之前，页面上所有 `setTimeout`/点击回调都排在队列里。表现是「点击没反应/切页迟钝」，不是 ANR。
- 真正会上 UI 线程的是 `runOnUiSync()`（`QqbotActivity.java:268-283`）派发的任务 —— `doCopy / doToast / doOpenTerminal / doOpenPanel / doOpenUrl / doOpenQqGroup`（`QqbotActivity.java:178-243`）。这个方法是设计得好的：`CountDownLatch` + **最多等 3 秒**，超时返回 null 并让调用方报失败，**绝不让页面卡死**。

**结论**：B 题的主要矛盾不是「UI 线程做 IO」，而是「**JS 桥线程被同步调用塞满了**」。

## 4. C —— 沙盒守护进程开销

### 4.1 `run-all.sh`（supervisor，每 3 秒一轮）

`build/opt/qqbot/sandbox/run-all.sh:95-121` 的主循环每轮做：

| 动作 | 位置 | 开销 |
|---|---|---|
| `off napcat` → `[ -f "$SVC/napcat.off" ]` | `:15`、`:96` | 1 次 stat |
| `kill -0 "$NP"` | `:99` | 1 次 syscall |
| `off astrbot` | `:96` 同构 | 1 次 stat |
| `kill -0 "$AP"` | `:111` | 1 次 syscall |
| `sleep 3` | `:120` | **1 次 fork + exec**（`/bin/sleep`） |

**稳态每 3 秒 = 2 stat + 2 kill -0 + 1 次 fork/exec。** 按量级算是 0.33 次 exec/秒。

另有 `run-all.sh:87-89` 的 60 秒 `trim_logs` 子 shell，每次对每个 `*.log` 做一次 `stat -c %s`（每次一个 fork/exec），超过 20 MB 时 `tail -c 2097152` + 原地截断。**这个设计是对的**：注释 `:17-19` 解释了必须原地截断（否则持有旧 fd 的服务会继续写已删除的 inode）。

**关键放大器：这一切发生在 proot 里。** proot 用 `ptrace` 拦截每个 syscall 做路径翻译，`fork/exec` 在 proot 内的成本显著高于原生（要为子进程重建翻译表）。因此「1 次 `sleep 3`」在 proot 下的实际 CPU 时间不是零。

**量级估算**（估算，无设备实测）：`sleep` 本身几乎不耗 CPU，但 proot 的 ptrace 唤醒 + 路径翻译在每次 fork/exec 上留 5~20 ms 量级的内核时间 → **每 3 秒约 5~20 ms CPU**（约 0.2%~0.7% 单核）。**这条本身不是耗电主因。**

### 4.2 run-napcat.sh 每 5 秒的隐藏成本（比 run-all.sh 重得多）

`build/opt/qqbot/sandbox/run-napcat.sh`（608 行）主循环每轮：
1. `read_bots()` → **1 次 `python3` fork/exec**（解析 `bots.json`）
2. 对每个正在启停的实例：`napcat_inst_value()` 每个字段一次 `python3`（`token / napcatPort / qq` 共 **3 次**）、`write_onebot` **1 次**、`write_napcat` **1 次** → 单实例启动时 **5 次额外 `python3`**（仅启动那一轮）
3. 稳态每轮：**1 次 `python3`** + `sleep 5 & wait`（1 次 fork/exec）

**python3 冷启动在 proot 内是 100~300 ms 量级**（估算）。稳态 = 每 5 秒一次 python3 → 若按 200 ms 算，**约 4% 的单核占用**。启动/重启实例时那 5 次 python3 会有一次 ~1 秒的尖峰。

**改法（按性价比）**：
1. **`read_bots()` 换成纯 shell 的 `sed` 解析**，与 `common.sh` 的 `qq_napcat_port()/qq_onebot_port()`（`build/opt/qqbot/common.sh:87-149`）保持一致的做法。代价是失去「解析失败 → `__SKIP__`」的数据安全保护（`run-napcat.sh` 注释里明说是**数据丢失级**风险的防护），**不建议直接换**——但可以改成「先 `sed` 快速取，取不到或结构可疑时才 fallback 到 python3」，稳态下 90% 的轮次不需要 python3。
2. **`napcat_inst_value()` 三次调用合并成一次 python3**，一次输出 `token|napPort|qq` 三行。收益：启动尖峰 -3 次 python3。
3. **降低轮询频率**：5 秒对「用户在 WebUI 上点启用/禁用实例」来说足够快，其实 **10 秒**完全够用，能直接砍掉一半 python3 启动。风险：用户点开关后最多 10 秒才生效。

### 4.3 常驻内存量级（**估算**，无设备实测）

| 组件 | 常驻 RSS 量级 | 依据 |
|---|---|---|
| NapCat（QQ NT / Electron） | **约 350~700 MB** | Chromium 内核典型构成：主进程 + 渲染进程 + GPU 进程 + zygote；`run-napcat.sh` 用 `xvfb-run` 起 `qq --no-sandbox`，**没有**独立显存，所有合成在 CPU 上做（软件渲染），内存与 CPU 都更贵 |

### 4.4 待机耗电与唤醒（定量估算）

**唤醒次数**（稳态，全部来自轮询）：

| 来源 | 周期 | 次/天 |
|---|---|---|
| supervisor 主循环 | 3 s | 28,800 |
| run-napcat 主循环（含 1 次 python3） | 5 s | 17,280 |
| trim_logs | 60 s | 1,440 |
| **合计** | | **约 47,500 次/天** |

**关键事实**：`deploy.sh:26-28` 只在**部署期**申请 `termux-wake-lock`。部署完成后没有 wake lock → 按 Android 的电源模型，进程会随时被冻结（Doze/App Standby 下更激进）。

**推论（重要，与直觉相反）**：
- **有 wake lock 时**：47,500 次唤醒/天，每次含 proot ptrace + fork/exec，是实打实的耗电来源。
- **无 wake lock 时**：这些定时器会被系统冻结/合并，实际耗电反而低，但**NapCat 与 AstrBot 的 WebSocket 长连接会断**（表现为「放置一段时间后掉线，回来要重连」）。

因此**「待机耗电」和「后台保活」在架构上是一对矛盾**，当前代码选择了保活（因为 NapCat 必须一直在线收消息）。真正能优化的只有：
1. 把 `run-all.sh:120` 的 `sleep 3` 提到 **5 秒**（与 run-napcat 对齐），唤醒次数 47,500 → 34,600 **-27%**。服务崩溃到被拉起的延迟从 3 秒变 5 秒，对 IM 机器人无感。
2. `run-napcat.sh` 的 5 秒轮询提到 **10 秒**（见 4.2 改法 3），再 -8,600 次/天。
3. 两项合计：**47,500 → 26,000 次/天（-45%）**。

**注意**：这些优化对电量的绝对影响是**小头**（几十毫安时级别）；真正的耗电是 **NapCat 的 Chromium 常驻 + Xvfb 软件渲染**。若要真正省电，方向是「不用 xvfb-run + Electron，改用 NapCat 的无头/纯 Node 模式」——但那是架构级改动，超出本次审计范围。

### 5.3 可压缩空间（按收益排序）

#### D-1 把三份大下载从关键路径上摘出来并行（收益最大）

- **现象**：`40-qq`（198 MB）、`50-napcat`（34 MB）、`60-astrbot`（9 MB）全部在各自步骤**开始时串行下载**，而下载期 CPU 与磁盘几乎空闲。
- **证据**：`build/opt/qqbot/steps/40-qq.sh`、`steps/50-napcat.sh`、`steps/60-astrbot.sh` 各自的 `qq_dl_mirror` / `qq_gh_dl` 调用；下载函数在 `build/opt/qqbot/common.sh:272-307`。
- **改法**：新增一个 `05-prefetch.sh`（或放在 `10-termux` 之后、`20-rootfs` 之前）**并行**在后台 `&` 拉取这三份到 `$QQBOT_CACHE`，主流程照常跑 `20-rootfs` / `30-apt`；到 `40-qq` 时文件已在本地，步骤内的下载自然跳过（脚本本来就是「缺则下载」）。三个 curl 并行还能吃掉单连接的带宽浪费。
- **收益**：**下载时间（198+34+9 = 241 MB）从关键路径上消失**。按 2 MB/s 算省约 2 分钟，按 500 KB/s 算省约 8 分钟 —— **占总时长 8%~25%**。而且它同时把 `50-napcat` 的「9 个镜像依次重试」的失败等待也提前化解了（`common.sh:298-307` 是逐个镜像试，失败要等 `--connect-timeout 20 ` 甚至 `--max-time`）。
- **风险**：中。要注意 ①并行下载与 `apt-get update` 抢带宽（可以把并发降到 2）；②三个后台 curl 的失败不能影响主流程（各自独立 fail-safe）；③`deploy.pid` 并发护栏（`deploy.sh:11-17`）不受影响，因为这是同一次部署内的子进程。

#### D-2 换掉 `fonts-noto-cjk`（单点收益最大）

- **现象**：`30-apt.sh` 第 2 批装 `fonts-noto-cjk fonts-wqy-zenhei fonts-dejavu-core` 三个字体包，其中 `fonts-noto-cjk` 是**整个部署里解包体积最大的单一依赖**（含多字重、覆盖 CJK 全字符集）。
- **证据**：`build/opt/qqbot/sandbox/30-apt.sh` 第 2 批；源码注释自述 Noto CJK 通常 100~300 MB 解包。
- **改法**：三选一 —— ① 只留 `fonts-wqy-zenhei`（约 15~20 MB，足够让 QQ 界面显示中文），删掉 `fonts-noto-cjk`；② 换 `fonts-noto-cjk` 为 `fonts-noto-cjk-extra` 之外的最小等价（如 `fonts-arphic-uming`）；③ 保留下载但用 `--no-install-recommends`（**已开**）再加 `apt-get download` + 手动只解包需要的 `.ttc`。
- **收益**：解包 100~300 MB 的 I/O 与 dpkg 时间，**估 3~6 分钟，占总时长 10%~20%**；同时省 100~300 MB 的沙盒存储。
- **风险**：**中偏高**。删掉 Noto 后，某些 emoji / 生僻字 / 韩文日文会变方块。**必须先在一台真机上试**。折中方案：默认装 wqy-zenhei，把 noto-cjk 做成「设置页可选安装」。

#### D-3 `40-qq` 的 deb 下载没有真正利用多镜像

- **现象**：`steps/40-qq.sh` 走的是 `qq_dl_mirror`（顺序尝试），而且 QQ deb 只有 `QQBOT_QQ_DEB_BASE`（`common.sh:20-22`）一个上游 + 代理，不像 GitHub 资源那样有 9 个镜像。
- **证据**：`build/opt/qqbot/common.sh:20-22`（`QQBOT_QQ_DEB_BASE="https://qqdl.gtimg.cn/qqfile/QQNT/9.9.36/beta/9ee04bef"`）。
- **改法**：加多源（腾讯 CDN 的其它 path、镜像站、或让用户在设置页填自己的直链）。另外 `qq_dl()`（`common.sh:272-281`）已带 `--retry 3 --retry-delay 3`，但 198 MB 单连接慢速下载**不会**因为 retry 而变快 —— 值得切成 HTTP Range 多连接（`curl -r` 分段并发）。
- **收益**：在慢网（500 KB/s）下 198 MB 需要约 6.6 分钟，4 段并发可降到约 2 分钟，**省 4 分钟（约 13%）**。
- **风险**：中。`qqdl.gtimg.cn` 未必支持 Range；需要 fallback 到单连接。

#### D-4 `50-napcat` 的 9 镜像轮询可能吃掉几分钟

- **现象**：`common.sh:298-307` 的 `qq_gh_dl()` 把 9 个镜像前缀各拼一遍 + 原 URL 放最后，交给 `qq_dl_mirror()` **逐个**试。
- **证据**：`build/opt/qqbot/common.sh:25-27`（9 个镜像）、`common.sh:283-296`（`qq_dl_mirror` 逐个试）、`common.sh` 的 `qq_dl` 默认 `--connect-timeout 20`、`--retry 3 --retry-delay 3`。
- **量化**：一个镜像「连不上」最坏 = 20 s（connect timeout）× 3 次 retry + 2 次 3 s delay ≈ **66 秒**。9 个镜像全部不可用 = **约 10 分钟纯等待**。
- **改法**：① `--retry` 从 3 降到 1，并把 `--connect-timeout` 从 20 降到 8（连不上就是连不上，重试 3 次不会变好）；② 用 `curl -L -m 30 --speed-time 10 --speed-limit 10240` 做「慢速即放弃」，避免一个能连上但龟速的镜像把 1800 秒的 `--max-time`（`common.sh:272-281` 的默认 `_t`）耗光；③ 让 9 个镜像**并发探测**（`curl -I` 并发取最小 RTT），选最快的那个再下。
- **收益**：最坏情况省 5~10 分钟；正常情况省几十秒。
- **风险**：低。

#### D-5 已经做对的地方（不要动）

- `deploy.sh:51-72` 的**断点续跑**：每个步骤成功即 `: > "$QQBOT_STEPS/$s"`，失败重跑时跳过已完成步骤。这是「20~60 分钟」能被容忍的关键设计。
- `deploy.sh:11-17` 的**并发护栏**（`deploy.pid` + `kill -0`）：防止 profile.d（`etc/profile.d/50-qqbot-sandbox.sh`）每次登录都触发第二份部署。
- `20-rootfs.sh` 明确**不走 proot** 解包（注释解释了 houdini 翻译下 ptrace 寄存器错配会挂死）—— 这是拿血的教训换来的，**必须保留**。
- `sandbox/extract.py` 的存在：因为 proot 5.5.0 的 `*at` 系统调用翻译 bug，`tar` / `dpkg-deb` 都会漏目录，Python 的 `tarfile/zipfile` 走普通路径解析才可靠。**不要为了"少一个文件"把它换回 tar。**
- `steps/40-qq.sh` 传**精确包名**而不是 `ls` glob（避免两架构 deb 并存时取错）。

### 5.4 D 题小结

**「首次部署 20~60 分钟」的可压缩空间约 30%~40%**，具体是：
- D-1 并行预下载：**省 8%~25%**（最值得做，风险中等）
- D-2 字体等价替换：**省 10%~20%**（最见效，但需真机验证中文显示）
- D-4 镜像探测优化：**最坏省 15%+**（低风险兜底）
- D-3 分段下载：省约 13%（慢网下）

三者叠加后，**典型首装可从约 30 分钟压到约 18~20 分钟**。

### 6.2 bootstrap 的真实结构（与直觉相反）

`libtermux-bootstrap.so` **不是**一个普通 .so，而是 **ELF64 外壳 + 内嵌 ZIP**：
- `e_shnum=22`，`.rodata` 从 off=**1328**、size=**29,388,907** —— 整个 bootstrap ZIP 就是 `.rodata` 的内容。
- 文件总长**恒为 29,392,992 B**；内嵌 ZIP 的首个 local header 在绝对偏移 1328，但中央目录里的 `cdOff` **需要 +1328 才是绝对位置**（repack 工具留下的一致性怪癖，解析时必须做偏移校正）。
- stock 版（`_research/libtermux-bootstrap.so`）：**3490 entries**，压缩 28,722,315 B，未压缩 70,758,704 B。
- 关键冗余：`share/man/man1|man3|man5|man7|man8` 全部 **method=0（存储、完全没压缩）**，共约 2.42 MB 纯浪费。

### 6.3 【独立判断】分发的 APK 是一个过期产物

**证据链（同一份 29,392,992 B 的 .so 外壳，内嵌内容不同）**：

| 产物 | 内嵌 zip entries | 内嵌 sum_c |
|---|---|---|
| `QQBot-Sandbox.apk` | 1775 | 21.97 MB |
| `out/signed/...debugSigned.apk` | **750** | **18.31 MB** |

内层少 3.66 MB 压缩内容 → 外层 APK `25,072,546 vs 28,925,032`，**差 3,852,486 B ≈ 3.85 MB（-13.3%）**。

`QQBot-Sandbox.apk` 里**仍然存在**（而 `build-apk.ps1` 的 `$dropPrefixes` 早已列入删除名单）：`include/`（约 1.5 MB 压缩，含 openssl/apt-pkg/event2/gnutls/bash 等一堆头文件）、`libexec/installed-tests/`（0.9 MB）、`libexec/termux-am/`（0.548 MB）、`libexec/termux/`、`lib/bash/`、`lib/gawk/`、`lib/pkgconfig/`、`lib/cmake/`、`share/aclocal`、`share/nano`、`share/bash-completion`、`share/readline`。

**❗ 更严重的问题：分发的 APK 里的 shell 脚本是旧版本的。**

对比内嵌 `opt/qqbot/` 脚本的 usize（分发 APK / signed APK / 当前源码）：

| 脚本 | 分发 | signed | 源码 |
|---|---|---|---|
| `opt/qqbot/common.sh` | 14,464 | 17,531 | 18,222 |
| `opt/qqbot/sandbox/run-napcat.sh` | 14,851 | **24,746** | 24,746 |
| `opt/qqbot/sandbox/50-napcat.sh` | 4,488 | **10,197** | 10,197 |
| `opt/qqbot/sandbox/60-astrbot.sh` | 4,184 | 5,955 | 6,687 |
| `opt/qqbot/start-sandbox.sh` | 3,476 | 3,476 | 4,102 |
| `opt/qqbot/steps/70-launcher.sh` | 5,859 | 5,859 | 6,274 |

分发版**缺了 `run-napcat.sh` 约 10 KB 的后期修复**（多实例 `__SKIP__` 数据保护、`purge` 防护、`cleanup` 的 `exit 0` 等 —— 这些都是注释里标为「数据丢失级」的修复）。

**结论与建议**：
1. **立刻改发 `out/signed/termux-qqbot-aligned-debugSigned.apk`**（23.91 MB）。一次性省 3.85 MB，且脚本是新的。
2. 或者：在 `build-apk.ps1` 流水线上**重跑一次**，让 `QQBot-Sandbox.apk` 从当前 `$dropPrefixes` + 当前 `build/` 目录重新生成。
3. **注意 `build/` 是整体注入的**（`build-apk.ps1` 的 `Get-ChildItem -Recurse -File $BUILD`），所以 `build/` 下任何临时文件/编辑器备份（`*~`、`.swp`、`*.bak`）都会被打进 APK。建议在构建前加一道白名单/黑名单过滤。

### 6.4 还能再减什么（独立判断）

| 目标 | 可省 | 风险 | 值不值得做 |

### 已落地（5 项）

1. **去掉重复的 2 秒 `refreshDeploy()`** —— `ui/assets/qqbot/index.html` 删掉独立那条 `setInterval(...refreshDeploy...,2000)`，以及 `visibilitychange` 尾部那次（`refresh()` 内部已含）。
   `deployInfo()` 调用频率 0.75 次/秒 → **0.25 次/秒**。
2. **日志只读一次** —— 新增 `readLogShared(name, lines)`（1.2 秒 TTL 缓存），`loadLog()` 与 `loadDuo()` 共用同一份
   `Android.readLog(name, 400)` 结果，不再各读一遍同一个 `qq-<id>.log`；`doClearLog()` / `doRmLog()` 之后调
   `dropLogCache(name)` 立刻作废缓存。真机验证：清空 `astrbot.log`（1,725,014 B → 0 B）后界面立刻显示
   「（astrbot.log 暂无内容）」，缓存失效正确。
3. **`state()` 只读一次 `bots.json`** —— 新增 `QqbotActivity.astrbotPortOf(JSONObject)` /
   `astrbotPortRawOf(JSONObject)` 两个重载，`QqbotBridge.state()` 内部解析一次后复用（原来读 3 遍、解析 3 遍）。
4. **`tail()` 改成从文件尾反向逐块数换行** —— `QqbotActivity.tail()` 用 32 KB 块从末尾往前扫，`MAXREAD` 上限 1 MB，
   按实际需要的行数只读那一段；不再无论要几行都读 256 KB。
5. **无限脉冲动画加合成层提示** —— `.pill.ok::before` 与 `.dot.ok,.dot.warn` 加 `will-change:opacity`，
   避免动画帧让祖先带 `backdrop-filter` 的卡片每帧重新栅格化；`loadLog()` 补上与 `setPre()` 一致的
   `if (box.textContent === t) return;` 守卫。

### 未采纳的两条及其证据

- **换掉 `fonts-noto-cjk`（报告第 5 条前半）** —— 已在设备上实测：临时移走 `/usr/share/fonts/opentype` 后
  `fc-match "sans-serif:lang=zh-cn"` 回退到 `wqy-zenhei.ttc`（中文可用），移除后 `fc-list :lang=zh` 只剩 3 条。
  **但收益不足**：89 MB 只占沙盒总占用 4237 MB 的 **2.1%**，下载侧也只省约 50 MB，
  而要付出 QQ 界面中文观感下降的代价 —— 不划算，**保持现状**。
- **部署期并行预下载（报告第 5 条后半）** —— NapCat(34 MB)+AstrBot(9 MB) 合计 43 MB，
  相对整体 250 MB 下载与 24~38 min 首装时长只省几十秒；且要动 `deploy.sh` 步骤表与前端硬编码的 7 步，
  风险收益比不成立 —— **暂不做**。

### 关于 20%~28% 的 CPU 判读

它不是卡顿：掉帧率 0.44%、GPU 仅 1 ms，界面是流畅的。这 60 fps 的持续渲染来自设计上的
「在线」脉冲动画（`@keyframes breathe` 无限循环）。模拟器无硬件 GPU 加速时，软件合成 60 fps 的开销
几乎全落在 CPU 上；真机有 GPU 合成时这部分会显著更低。若将来仍要压低，
下一步应减少同时呼吸的元素数量（当前主页约 4 枚 pill + 每张卡片头部 1 枚 dot），而不是动毛玻璃参数。
